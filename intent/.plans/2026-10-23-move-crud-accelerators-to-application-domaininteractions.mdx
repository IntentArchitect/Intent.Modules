# Move CRUD accelerators out of Modelers.Services.DomainInteractions

## Context

`Intent.Modelers.Services.DomainInteractions` (this repo, v2.4.8) should only hold **intention** concerns: the Create, Update, Delete and Query Entity Action associations, their mapping settings, and Processing Action. It also ships every CRUD accelerator that *generates* those intentions on a domain entity. Those move to **`Intent.Application.DomainInteractions`** in Intent.Modules.NET, v1.2.10. That module already depends on the designer module, every .NET CRUD module (MediatR.CRUD, CQRS.CRUD, ServiceImplementations.Conventions.CRUD) depends on it, and its v1.0.1 release note says it took the dependency precisely "to enable Domain suggestions for creating CRUD services".

**One example.** Today a user right-clicks a Services folder and picks **Create CRUD CQRS Operations** (alt+c), or uses the **Create CRUD CQRS Services in Services designer** suggestion on a Domain `Customer` class. After this change both behave the same, but the menu items, suggestions and the *Crud Api* script library come from `Intent.Application.DomainInteractions`. With only the designer module installed, neither appears.

## Decisions (settled)

| Decision | Choice |
|---|---|
| New home | `Intent.Application.DomainInteractions` (Modules.NET) |
| Basic-mode (legacy inline) CRUD scripts | Move them as well as the advanced ones |
| Sync with Entity suggestions, Create new result DTO, Convert to advanced mapping | **Stay** in the designer module |
| `Default Mapping Mode` module setting | **Stays** in the designer module. Modelers.Services, Services.CQRS and Common.CSharp read it, and the moved scripts keep reading it by setting id |

<Callout id="java-node" tone="warning" title="Java and NodeJS lose the accelerators">

`Intent.Java.Services.CRUD` and `Intent.NodeJS.Services.CRUD` depend on the designer module, at 1.0.3 and 1.0.4. Once a user on those stacks updates the designer module past 2.5.0, the CRUD accelerators disappear for them. This was accepted when Modules.NET was chosen as the home.

</Callout>

**Copy each element verbatim**, apart from the script ids it references. Keep every element's script text, `isOptionVisibleFunction`/filter, shortcut, icon, order, group and type targets exactly. Read the source with `run_designer_query`, then recreate it with `run_designer_script`. Copy the Domain suggestions' `navigateToDesigner` scripts as they are, swapping in the new Crud Api and Repository Operation Api script ids that the target app returns.

The Application.DomainInteractions Module Builder currently holds only a Factory Extension. It needs metadata package references for **Services**, **Domain** and **Domain.Repositories** so the extensions and suggestions can target those element types.

<Callout id="upgrade-order" tone="decision" title="Keeping both modules in step on upgrade">

Two failure modes:

- **New Application.DomainInteractions with the old designer module:** every menu item appears twice. Fixed by raising its dependency on the designer module to 2.5.0.
- **New designer module with the old Application.DomainInteractions:** the CRUD accelerators vanish. Fixed by the designer module's new interoperability `detect`: when `Intent.Application.DomainInteractions` is installed, it installs 1.3.0. This repeats the module's existing `detect` for `Intent.Application.MediatR.CRUD`.

</Callout>

<Callout id="cross-repo-path" tone="warning" title="Cross-repo tsconfig path">

The `outFile` only resolves when Intent.Modules and Intent.Modules.NET are siblings, for example `D:\Dev\`. From a worktree it does not. That matches the existing Pagination precedent and is accepted. In this task, compile with an explicit `--outFile` to the Modules.NET worktree.

</Callout>

## How the work is split across the repos

There is one Intent Architect workspace, holding both repos' solutions, and two Claude sessions.

| Who | Does what | Why there |
|---|---|---|
| **This session** (rooted in the Intent.Modules worktree) | All Module Builder work in **both** repos, the `.js` move and the Intent.Modules close-out | The element copy needs both models live: read the source with `run_designer_query`, write the target with `run_designer_script` |
| **A Modules.NET session** (rooted in the Modules.NET worktree) | The Modules.NET file-level close-out and commit | Modules.NET has its own `.claude` gate hook, which only checks edits made from a session rooted there |

<Callout id="release-together" tone="warning" title="The two PRs ship in the same release">

Application.DomainInteractions 1.3.0 depends on designer module 2.5.0. The designer module's new interop `detect` installs Application.DomainInteractions 1.3.0. Each one points at the other's new version, so neither PR can be released on its own.

</Callout>

## Steps

### Part A — this session

1. **Workspace setup.**
    - Create the Modules.NET worktree: `git -C D:\Dev\Intent.Modules.NET worktree add -b workitem/crud-suggestions D:\.worktrees\Intent.Modules.NET\workitem\crud-suggestions development`.
    - **You** then add that worktree's `Modules\Intent.Modules.NET.isln` to the open Intent Architect workspace.
    - Confirm `get_applications` lists the Application.DomainInteractions application before continuing.
    - Read both modules' `CONTEXT.md`. Application.DomainInteractions has none yet.
2. **Version gate** (`module-version-increment`), done through the Module Builder model:
    - Designer module 2.4.8 → **2.5.0-pre.0**. Removing functionality is a minor change.
    - Application.DomainInteractions 1.2.10 → **1.3.0-pre.0**.
    - Leave either alone if it is already in flight.
3. **Build the new home first.** In the Application.DomainInteractions Module Builder:
    - Add the metadata references.
    - Add the two Designer Settings and the two Scripts.
    - Add the Package and Element Extensions, the Services and Domain Suggestions, and the documentation topics, all copied from the source elements (see Model changes).
    - Repoint the two `DesignerMacros` tsconfigs' `outFile`. Produce `resources/crud-api.js` and `repository-operation-api.js` in Modules.NET by compiling with an explicit `--outFile` to the worktree, rather than copying the files.
    - Run `git diff --no-index` against the designer module's current files and confirm they match.
4. **Regenerate and build the new home, with the designer module still intact.** Run the Software Factory and `dotnet build --no-incremental` for Application.DomainInteractions. In the test app every CRUD menu option now appears **twice**. This is the expected interim state, and it proves the new copies are wired up.
5. **Strip the designer module.**
    - Delete the moved elements, both scripts and both `.js` files.
    - Delete the `docs/images/` screenshots used only by the moved README sections: `cqrs-repository.png`, `traditional-repository.png`, `repository-suggestion.png`, `add-repository.png`.
    - Keep the Entity Action associations, mapping settings, Processing Action, Sync, Result DTO Helper, Convert to advanced mapping and all three settings.
    - Update the `Default Mapping Mode` hint, add the interop `detect`, then regenerate and build.
6. **Inspect both `.designer.settings` diffs.** The CRUD option, suggestion and script blocks should have left the designer module and arrived in Application.DomainInteractions with the same script bodies.
7. **Intent.Modules close-out** (`module-dependency-audit`, `module-docs-chore`, `module-context-capture`):
    - Add a release note that the CRUD accelerators moved.
    - Remove the repository-operation accelerator section from the README, and change the intro so it no longer reads "designer support for our CRUD Modules".
    - Drop `crud` from the `.imodspec` `<tags>`.
    - Record in `CONTEXT.md`: *"intention only — CRUD generation lives in Intent.Application.DomainInteractions"*.
    - Make one commit.
8. **Hand-off.** Leave the Modules.NET worktree uncommitted and tell you to start a session in it with the prompt below.
