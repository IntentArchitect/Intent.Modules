# Context: Intent.Metadata.WebApi

## Purpose

Designer metadata for describing services as HTTP endpoints: the `Http Settings`, `Parameter Settings`, `Api Version Settings` and related stereotypes on the Services and Service Proxies designers, plus the designer scripts that keep an endpoint's route in step with its parameters and validate it. It generates no code. Other modules (controllers, proxies, OpenAPI) read its stereotypes through the extension methods in `Api/`.

## Architectural Decisions

- **Route parameters are matched ignoring case, in every ASP.NET Core form.** ASP.NET Core binds `{CacheKey}` to a parameter named `cacheKey`, so the designer has to as well. Both `updateRouteParameters` and the route validation recognise `{name}`, `{name:constraint}`, `{name?}`, `{name=default}`, `{*name}` and `{**name}`, and compare names without regard to case. The update script also accepts the `toCamelCase` form of a name, because that is the form it appends, and `toCamelCase` drops spaces and underscores (`Cache Key` becomes `cacheKey`). Before 4.7.22 the script matched with exact-case `indexOf` on `{name}` and `{name:` only, so a `{CacheKey}` route got `/{cacheKey}` appended on every on-changed event, and the user had no way to undo it.
  - Rejected: stop appending missing route parameters and rely on validation instead. Appending is long-standing behaviour that users rely on when they switch a parameter to `From Route`, and validation already reports a route that still lacks the parameter.
- **A case-only rename leaves the route alone.** `getPreviousName()` keeps returning the old name until the element is renamed again, so the rename block re-runs on every later change. Without this check, a case-only rename would rewrite the user's `{CacheKey}` to `{cacheKey}`.
- **An empty Route is valid.** An `Operation` with no Route answers on its `Service`'s route, which is what an ASP.NET Core action with no template does on its controller's route. So validation reads a null Route as `""` and checks the `Operation` against the `Service`'s route, and two route-less `POST`s on one `Service` are duplicates. A `Command` or `Query` with no Route has no route to check. Brownfield import produces this state for every action attribute with no template, such as a bare `[HttpPost]`. Before 4.7.22 a null Route threw `TypeError` in `normalizeRoutePath`.
  - Rejected: reporting an empty Route as an error. It is a legitimate model of real code.
- **Each element is checked against the others, and none of them may stop that check.** Validation runs once per element, and each run builds the route of every `Command`, `Query` and `Operation` in the designer to look for duplicates. Building a candidate's route is wrapped in `try`/`catch` and a failing candidate is skipped. The element's own route is built outside the `try`, so its own failure still reaches Intent Architect. Before 4.7.22, one null Route made every HTTP element's validation throw, and Intent Architect treats a throwing validation function as "no error", so duplicate and parameter checks were silently off for the whole designer.
  - Rejected: wrapping the whole function. It would also hide the element's own failure.
- **Per-evaluation work is kept to what the check needs.** `__getRouteParameterExclusions()` reads two application settings, so it runs once per evaluation and its result is passed into every `RestRoute`, not once per route built. A candidate's verb is read before its route is built, because only a same-verb route can be a duplicate. On a mock of a 151-endpoint designer this cut `getSettings` calls per pass from 91,808 to 604, and `getStereotype` calls from 267k to 186k.
  - **Limitation — validation functions share no state across one pass.** Each element's validation runs on its own, so a pass is still O(n²) in `getStereotype` calls. Making it linear, by building a route index once per pass and looking each element up in it, needs a per-pass cache from Intent Architect that the validation API does not offer.
  - Rejected: caching the index on a global. Nothing signals the end of a pass or a model change, so a cached index would report stale routes after an edit.

## Invariants & Constraints

- **The update script and the validation must agree on what a route parameter is.** `getRouteParameterNames` / `renameRouteParameter` in the update script, and the parameter extraction in `RestRoute`'s constructor in the validation, must recognise the same forms. If they disagree, the script leaves a route alone that validation then rejects, or appends a segment that validation would have accepted.
- **Every script that reads `Http Settings` → `Route` must accept a null value, not only `""`.** Brownfield import leaves the Route null for an action with no template. Two scripts read it at validation time: the route validation, and the `Http Settings` stereotype definition's own Validate Function, which reports a `//` in the Route. Before 4.7.22 the latter called `route.includes` on `undefined`, which logged a `TypeError` on every pass for each route-less endpoint.
- **The route scripts are maintained in different places.**
  - The route update functions (`updateVersionParameter`, `updateRouteParameters` and their helpers) are an inline script on the `HTTP Route Update Scripts` Script element in this module's Module Builder designer. There is no TypeScript source for them.
  - The route validation is TypeScript in `DesignerMacros/src/services-rest-route-validation/` at the repository root. Compile it with `tsc -p <command|query|operation>/tsconfig.json`, then set the `_dist.js` output as the `Validate Function` of all three Element Extensions: `Command Extension` and `Query Extension` under `WebApi CQRS Extensions`, and `Operation Extension` under `WebApi Services Extensions`. Each model copy is expected to equal its compiled `_dist.js` exactly, line endings aside, so diff before replacing one. `_dist.js` is gitignored (`DesignerMacros/.gitignore` ignores `**/*.js`), so the model copies are the only committed compiled output.
  - The `//` check on `Http Settings` → `Route` is an inline Validate Function on the `Http Settings` stereotype definition, also with no TypeScript source.
- **Script element functions share a scope with the designer's other scripts.** The on-changed event handlers call `updateRouteParameters` from a different element, so a helper name added to the Script element can collide with a function defined by another script. Check new names against the other `.designer.settings` scripts in this repository and Intent.Modules.NET.
- **The Software Factory does not write `.imodspec`, the `.csproj` or `release-notes.md` here**, because all three are file-level ignored in this application. To move the version, set `Module Settings` → `Version` in the Module Builder designer, then edit `.imodspec` `<version>` and `.csproj` `<Version>` by hand. Release notes are hand-maintained.
- **`Intent.Modelers.Services.CQRS` is not a declared dependency, although `Api/` uses its models.** It was removed by hand from `.imodspec`, together with `Intent.Modelers.ServiceProxies` and `Intent.Modelers.Types.ServiceProxies`, in 4.4.3-pre.2 (commit 11729c970, "ignore on imodspec to allow metadata on proxies"), when the file was made file-level ignored. A dependency audit will flag it. Find out why it was removed before re-adding it.
