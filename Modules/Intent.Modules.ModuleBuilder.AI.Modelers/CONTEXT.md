# Context: Intent.ModuleBuilder.AI.Modelers

## Purpose

Bundles one Intent Architect AI agent skill, `intent-modelers-integration`, into the consuming repo's `.agents/` folder. The skill documents how another module integrates with Intent Architect's own built-in Domain, Services, Eventing, and User Interface designers — install identity, entry points, elements, associations, stereotypes, a worked snippet, and a complete member-level model API reference per designer, with each designer's extension modules in a separate `*-extensions.md` resource. Every bundled file is generated from this module's own source and always overwritten on install/update — there is no per-repo customization and no settings gating which content is included.

## Architectural Decisions

- **One skill, not four.** The router (an agent's skill-description scan) only sees `SKILL.md` files. Splitting per designer into four separate skills would multiply router entries for what is one coherent question — "how do I wire a module against a Modelers designer" — and would force an agent working across two designers to load two unrelated SKILL.md frontmatter blocks. Instead there is one skill with resource files loaded on demand: `integration-recipe.md`, one per designer, and one `*-extensions.md` per designer that has extension modules.
- **Extension modules live in their own resource file per designer, not in the base designer's file** (split in `1.0.0-pre.2`, at the maintainer's direction). An extension module is a separate install with its own identity, and most modules integrating with a designer never touch one. Keeping them in `domain.md` etc. made every base read pay for up to five extension modules' identities and ~350–600 lines of their API stubs. Files: `domain-extensions.md`, `services-extensions.md`, `user-interface-extensions.md`. Each has §1 install identities (the former base §8), §2 model API reference (the former base §10.2+) and §3 collisions that involve an extension module. Base files dropped §8 and renumbered: §8 Worked snippet, §9 Model API reference. Collisions between a base designer and `Common.Types` or another base designer stay in the base file. Rejected: one combined `extension-modules.md` for all designers, because an agent working on Domain would also load Services/UI extension content, against the per-designer loading rule. **Eventing has no extensions file**: it has no extension modules, and a file saying "none" would only cost a read, so `eventing.md` §1 states it instead.
  - **Invariant: every extension module stays discoverable at all three hops, because moving it out of the base file hid it.** The split left three gaps: the skill `description` named no extension concept, the SKILL.md TIP linked "Domain extensions" without saying what was inside, and base §1 named only some modules. An agent looking for `StoredProcedureModel` or `CommandModel` could therefore miss the skill or the file entirely. Each extension module, and its headline model types, must now appear in (1) the `description`'s extension-module list, (2) the TIP line beside its extensions-file link, and (3) the "Extension modules — read `<designer>-extensions.md`" paragraph at the end of the base file's §1. When an extension module is added or removed, update all three alongside the extensions file.
- **Completeness over brevity in the resource files, deliberately.** `SKILL.md` stays short because it loads on every router match; the resource files load only when an agent actually needs that designer, so length there is not a cost the way it is in `SKILL.md`. Each resource file was authored by exhaustively enumerating that designer's own `Api/` folder rather than sampling — a resource file that silently omits an element type is the exact failure mode this skill exists to prevent (an agent that can't find `LayoutSiderModel` concludes it doesn't exist).
- **Every extension module gets its own full install identity, never just a name.** Verified while authoring: no two sibling extension modules of the same base designer are guaranteed to follow the same `Modules.`-segment convention in their NuGet id / module id / namespace. Domain alone has five extension modules and at least two different conventions among them (`Domain.Services`' NuGet id drops `Modules.` entirely; `Domain.StoredProcedures` keeps `Modules.` in both its module id AND namespace, unlike its four siblings). Services' `.CQRS` was suspected of leaking `CommandModel`/`QueryModel` into the parent `Services.Api` namespace — verified false; it has its own isolated `Services.CQRS.Api`. The lesson generalized into `SKILL.md` Must #6 / Must Not #5: never infer one extension module's identity from a sibling's.
- **Four designers covered in the first cut, all confirmed via read-only research agents against live source** — not carried over from an earlier, less-verified draft. Domain, Services and Eventing's facts matched the working assumptions going in; User Interface had the most corrections (see below) and is the longest resource file as a result.
- **Deferred, not covered:** Service Proxies, Codebase Structure, Folder Structure, Module Builder, App Templates. The one-skill/per-designer-resource shape makes adding any of these later purely additive — a sixth resource file plus a link from `SKILL.md`'s TIP block, no restructuring.
- **No package dependency on `Intent.ModuleBuilder.AI.Skills`, matching that module's own recorded invariant.** `intent-metadata-consumer` (bundled by `AI.Skills`) and `intent-modelers-integration` (this module) sit at adjacent points on the same journey — this skill stops at "you now hold a `ClassModel`"; that one takes over there — but the cross-reference between them is a **soft, name-only pointer in each skill's `description`**, not an `.imodspec` `<dependency>`. Each bundle must remain independently installable.
- **User Interface corrections found during authoring, worth remembering because they are easy to re-assume incorrectly:** the accessor is `.UserInterface(app)`, not `.UI(...)`, confirmed verbatim in `ApiMetadataDesignerExtensions.cs`. The six trait interfaces (`IComponentModel`, `IComposableModel`, `IPageModel`, `IDialogModel`, `IInvokableModel`, `IInvokableServiceOperationModel`) live in `Intent.Modules.Modelers.UI.Api` — a different namespace from every concrete class, which lives in `Intent.Modelers.UI.Api`. Of the six, only `IComponentModel` and `IInvokableModel` are actually implemented by any shipped class; the other four are declared, documented, and have real extension-method receivers, but zero implementers — a template author must go through the concrete `ComponentModel` (e.g. `.Where(c => c.HasPage())`), not attempt to obtain an `IPageModel`.
- **Every designer resource carries a §9 "Model API reference", and each extensions file a §2 (added in `1.0.0-pre.2`), so agents stop reflecting over designer assemblies.** Before it, the resource files named each model class and a few navigation members, and an agent that needed `ClassModel.IsAbstract` or `DTOModel.ParentDto` fell back to `Assembly.LoadFrom`/`GetProperties()` against the NuGet DLL. Together they list every public type and member of each base designer and its extension modules, and `integration-recipe.md` §6 lists the SDK and `Common.Types` types those members return. `SKILL.md` Must Not #7 **discourages** reflection for anything these resources cover and allows falling back to XML docs or source when a member is genuinely missing, for example on a different pinned version. The maintainer asked for "discouraged", not an absolute ban, so keep that wording.
  - **Format: C#-style stubs, with shared members stated once.** Every generated model repeats the same identity members (`Id`/`Name`/`Comment`/`Stereotypes`/`InternalElement`), `Is<X>Model`/`As<X>Model` casts and ~20 association-end members. The base §9 header defines those once; each stub carries only a `// + common element members` marker plus its own members, and each extensions file's §2 defers to its base file's §9 for those conventions. Rejected: per-member markdown tables (roughly 3–4× longer for no added information), and full unfolded stubs (about 70% repetition that buries the members that differ).
  - **SDK surface lives once in `integration-recipe.md` §6, not in each designer file.** Rejected: duplicating ~250 lines four times. Each §9 points there.
  - **Scope:** each base designer plus every extension module in its extensions file. `Services.ProxyInteractions` ships no C# API, and `services-extensions.md` says so explicitly. `Intent.Modelers.Types.ServiceProxies` (home of `ServiceProxyModel`) is out of scope.
- **The API stubs are generated, never hand-typed — refresh them the same way.** The stubs were extracted with a throwaway Roslyn (`Microsoft.CodeAnalysis.CSharp`) script over `Modules/Intent.Modules.Modelers.*` source, then spliced into each partial's raw string before its closing delimiter. The splice was verified byte-identical in the regenerated `.md`. Hand-transcribing 2,500+ stub lines would reintroduce exactly the invented-member failure this reference exists to prevent. The extraction rules that must be reproduced:
  - **Input files:** `Api/**`, the root `ApiMetadata*.cs`, Eventing's root `MetadataManagerExtensions.cs`, root-level `*ExtensionModel.cs` (Domain.Events, Services.CQRS), and `Settings/ModuleSettingsExtensions.cs`. Skip `Migrations/`, `FactoryExtensions/`, `Templates/`, `obj/` and `bin/`.
  - **Partial classes:** merge all parts of a `partial` class across files before emitting. Services models have a hand-written second part.
  - **Common members:** fold them only after checking that each type actually has them. A type that derives from a concrete base (`FolderModel`, `DomainPackageModel`, …) gets `// + everything inherited from X` instead.
  - **Casts:** drop `Is*`/`As*(this ICanBeReferencedType)` methods, and keep everything else in those extension classes (`Has…Mapping`/`Get…Mapping`).
  - **Doc comments:** keep a type's or member's `<summary>` as a trailing `//` comment.
  - **SDK types:** the SDK interfaces in §6 were taken from `Intent.SoftwareFactory.SDK` `3.15.0` via `MetadataLoadContext`, because the SDK has no source in this repo. Parameter defaults were confirmed against `Intent.Modules.Common` source.
- **Eventing's publish/subscribe-filtered accessors live in a different file and a different namespace than every other provider in that module** — `MetadataManagerExtensions.cs` at the module root, namespace `Intent.Modules.Modelers.Eventing` (missing the `.Api` suffix every other file in that module has). Documented prominently in `eventing.md` §3 because it is exactly the kind of fact this skill exists to make lookupable instead of re-discovered.

## Critical Implementation Hazard

**Never edit a `...TemplatePartial.cs` markdown raw string with Intent's `patch_file`.** It re-indents the entire raw string to the constructor's nesting level and flattens the relative indentation inside every fenced code sample — silently; the tool reports success. Used `write_file` (full-content overwrite) for every one of this module's six template partials instead, and verified each via `get_file_diffs` before `apply_staged_file_changes`. Also apply from `Intent.ModuleBuilder.AI.Skills/CONTEXT.md`: the closing raw-string delimiter's indentation is load-bearing (at column 0 it compiles and packages while emitting an effectively empty document — check file _size_, not existence), a stray `---` toggles frontmatter mode, and `description` must stay a single physical line.

**A markdown list item must be one physical line.** `MarkdownFileBuilder` puts a blank line after the first line of a list item that wraps onto indented continuation lines. That splits the bullet in the generated `.md`, and the build and the SF run both report success. This hit every wrapped bullet in the first cut of the model API reference and was caught only by scanning the regenerated output. Paragraphs, tables and fenced code wrap safely; bullets do not. Scan the regenerated file for `^- .*\n\n  \S` after touching any list.

**A diff rebuilt from its `+` lines is not the file.** The Software Factory aligns new lines with identical old ones (the old trailing `}`/fence), so a context-free diff omits them. Verify generated content against the applied file on disk, not a diff reconstruction. A diff reconstruction falsely reported missing closing fences here.

- **`modules.config` is never hand-authored; the metadata-only install is what produces its entry.** `SKILL.md` originally listed `modules.config` alongside `.csproj` and `.imodspec` as a third file to write, which is wrong — it records what is actually installed, and editing it corrupts the application's module state. Corrected to: author two files, and obtain the third by installing the designer module with **`Install Designer Metadata` ticked and nothing else** (rarely also `Install Designers`). That choice is what yields `includeAssets="none"`; the attribute is a result, not an input. Ticking Factory Extensions, Application Settings or Template Outputs would pull the referenced designer's generation into an application whose only job is to *define* a module.

## Invariants & Constraints

- The skill's `File Template` (type `Single File`) sits directly under `Skills/` — no per-skill subfolder — named `IntentModelersIntegration_SkillMd_Agents` / `IntentModelersIntegration_Resources
  <Name>Md_Agents`, matching `Intent.ModuleBuilder.AI.Skills`' flat convention exactly. `File Settings(Output File Content=Text, Templating Method=Markdown File Builder)`; `Template Settings(Source=Lookup Type, Role=AI.Context.Skills)` with `Default Location` left **unset** — the `MarkdownFile` constructor's `relativeLocation` argument carries the real output path (`SkillName` for `SKILL.md`, `"intent-modelers-integration/resources"` for each resource file).
- This module has no `Module Settings Configuration` of its own — the bundled skill is unconditional, matching `AI.Skills`' precedent (settings-gated content belongs to `Intent.ModuleBuilder.AI.Workflow`, not here).
- `.csproj` mirrors `AI.Skills`/`AI.SDD` exactly: `Intent.Modules.Common` 3.11.4, `Intent.Packager` 3.6.0, `Intent.Persistence.SDK` 1.0.3, `Intent.RoslynWeaver.Attributes` 3.0.0, `Intent.SoftwareFactory.SDK` 3.15.0. `.imodspec` dependencies: `Intent.Common` + `Intent.Common.Types` only. `supportedClientVersions` matches `AI.Skills`: `[5.1.0-a,6.0.0-a)`.

## Module Interactions

- **Intent.ModuleBuilder.AI.Skills** — soft, name-only cross-reference only (see Architectural Decisions above). `AI.Skills`' `intent-metadata-consumer` skill was given one additional clause in its `description` naming this module, bumping `AI.Skills` from `1.0.1-pre.3` (itself a correction of a previously missed bump, recorded in `AI.Skills/CONTEXT.md`) to `1.0.1-pre.4`.
- **Intent.Modules.Modelers.{Domain,Services,Eventing,UI}(.*)** — read-only source of truth for every fact in the designer and extensions resource files, the API stubs included. Each stub block's heading records the source version it was extracted at, so a designer module moving on is the signal to re-extract. Not a package dependency; this module never installs against them, it only documents them.
- **Intent.SoftwareFactory.SDK / Intent.Modules.Common / Intent.Modules.Common.Types** — the source for `integration-recipe.md` §6. That section documents them; nothing here references them beyond the module's own `Intent.Common` dependency.
