# Context: Intent.ModuleBuilder.AI.Workflow

## Purpose

Bundles conditional, process-shaped AI agent workflow skills for the module-building lifecycle — when to increment a version, when and how to keep documentation current, when to capture durable context — into the consuming repo's `.agents/` folder. Unlike `Intent.ModuleBuilder.AI.Skills` (unconditional reference skills), every bundled skill here reads its own settings group and adapts its generated content accordingly.

## Architectural Decisions

- **No package dependency on `Intent.ModuleBuilder.AI.Skills`, by deliberate choice.** The two modules cover adjacent but decoupled ground (see that module's own `CONTEXT.md` for the mirror of this decision). Installing AI.Workflow must not pull in AI.Skills' whole bundle as a side effect.

- **`module-docs-chore` references `module-svg-icon` by name, but only as a soft, conditional pointer** ("if the `module-svg-icon` skill is available in your environment, use it") — never as a hard requirement. This is the first case where AI.Workflow content names an AI.Skills skill at all; it was a deliberate exception granted for this feature specifically, not a reversal of the no-dependency stance above. If AI.Skills isn't installed, the generated chore skill explicitly says to leave the module without an icon rather than improvising a substitute.

- **Icon creation is create-when-missing only — never a refresh.** An existing icon (however dated) is treated as a deliberate choice by whoever set it, mirroring how `docs/README.md` is created when absent but never forcibly rewritten wholesale. This is a narrower stance than release notes ("maintained, never introduced") and deliberately so: an icon is a visual asset a maintainer might hand-pick, unlike prose that this chore is expected to keep in sync with behaviour.

- **`MaintainModuleIcon` is a plain boolean, mirroring `MaintainModuleREADME` exactly** (`Switch` control, same accessor shape in `ModuleSettingsExtensions.cs`). No richer tri-state was added — off means "never touch icons," on means "create when missing."

- **`module-version-increment`'s major/minor/patch rubric judges impact on the user's experience, not a generic semver textbook rule.** The original table treated "new capability, setting, or generated file" as automatically Minor; Dandré rejected that after two changes that fit that description (`module-svg-icon`, `MaintainModuleIcon`) were both actually Patch. The replacement axis:
  - **Patch** — narrow impact (a setting affecting a small portion of the module, an addition alongside an already-established similar set), regardless of whether it's technically "new."
  - **Minor** — a genuinely new capability _dimension_ (Dandré's example: a module gaining the ability to generate templates tailored to a specific AI harness) — high impact, not breaking.
  - **Major** — changes how users already interact with the module (Dandré's example: adding a whole new designer to the module) — even with zero hard technical break, established habits or expectations can shift enough to need developer attention.

  Minor vs Patch is explicitly a magnitude judgment, not a checklist — being opt-in/off-by-default does not by itself make something Patch (`module-svg-icon` had no setting at all and was still Patch). Reasoning must be stated at the point of choosing, same as before.

- **Two gotchas were added to `module-version-increment`/`module-docs-chore` after a real consuming session tripped on both.** With `UsePreReleaseVersions` on, a developer corrected a module from `1.1.0` down to `1.0.3-pre.0`; the Software Factory silently reported nothing staged because `-pre.#` sorts _below_ the same `X.Y.Z` with no suffix — a downgrade by semver precedence, distinct from the already-documented local-compile trap. The same session then carried the `-pre.#` suffix into a `release-notes.md` heading, because the rule to strip it lived only in the opt-in `module-docs` skill, never in the routine `module-docs-chore` path that actually fires during ordinary work. Both gotchas are now documented where the routine path will actually see them.

- **The dependency audit is a close-out gate, not an opt-in pass.** A missing `.imodspec` dependency compiles cleanly and fails at _install_, in a consumer nobody can see — the exact failure class the workflow's "compiling is not working" rule exists for, and one no earlier phase can catch. So `module-dependency-audit` became the **fourth workflow skill**, wired into `module-building-workflow` at Phase 4 step 2: after Version (documentation refers to it) and before Documentation (a dependency fix is itself an observable change that then needs describing).
- **`Maintain Module Context` defaults to false, and false is exactly today's behaviour.** Off, `module-context-capture` only reads and maintains a `CONTEXT.md` that already exists — byte-identical to what shipped before the setting existed, so no consumer sees an unrequested change. On, it also creates one for a module that has none, but deliberately _not on arrival_: at the moment the first durable decision lands, because a `CONTEXT.md` of empty headings teaches the next session to skip the file.
- **Release-notes maintenance now consults `Module Settings → Include Release Notes` first.** Previously `module-docs-chore` decided purely on whether the file existed on disk, ignoring the checkbox that both states the maintainer's intent and drives `<releaseNotes>` in the manifest. Unticked means leave them alone; ticked-but-missing is reported as the inconsistency it is rather than silently fixed by creating the file.
- **This module's `Intent.Common` dependency floor is hand-set to match its compile-time reference, and that is expected to stay hand-set.** `IModSpecTemplate` seeds a fixed `Intent.Common` 3.7.2 baseline, so the Software Factory will never raise it on its own even though the `.csproj` compiles against `Intent.Modules.Common` 3.11.4 — a gap that compiles cleanly and would only surface when a consumer's install resolved the lower floor. Raised to 3.11.4 to match the `.csproj` and the sibling AI modules. It survives regeneration because dependency versions are only ever bumped _upward_: with the on-disk value higher than the computed one, the template leaves it alone. Verified by a no-op Software Factory run immediately after the edit.
- **The already-moved check is now a universal gate keyed on semver precedence, not an ad-hoc-only heuristic, and not a base-vs-exact split.** The prior `module-version-increment` had two disconnected paths: an up-front "just increment" step, and a separate "Ad-hoc Changes — Check Before You Move" section with a 4-step heuristic (task notes, version control, release notes, ask) scoped to changes that arrived already edited. Agents complied with "increment before you implement" on every new instruction and never reached the ad-hoc section, producing phantom prerelease bumps (`pre.4` → `pre.5` → `pre.6` …) for work still unpublished. Replaced both with a single `Is This Version Already In Flight?` section: a version moves only when a published version already exists **at or beyond it, by semver precedence** — checked via feed search with prereleases included, classifying the result's repository as a genuine sharing mechanism (URL, UNC, mapped drive, sync folder) versus the machine-local build-output one — with ask-the-developer as the sole fallback. An earlier draft of this rule stripped `-pre.#` and compared only the "base" version, on the theory that a prerelease line "consolidates" into its eventual final release; Dandré caught that this conflates two separate, independently-published version numbers (`1.0.1-pre.4` and `1.0.1` are not "the same," publishing one doesn't publish the other) — corrected to a single semver-precedence comparison with no base/exact split. Both `module-version-increment`'s own up-front step and `module-building-workflow`'s Phase 2/4 now reference this one gate, so every bump path runs the same test regardless of which document an agent read first.

- **(Superseded — nothing is written at the repository root any more: every hook template writes inside its own anchor, see the anchor decision below, and by Dandré's rule no root-level instruction file such as `AGENTS.md` is generated.) Reaching the repository root needs no new anchor.** `AGENTS.md`, `.codex/hooks.json`, `.kiro/hooks/*.json` and `.config/dotnet-tools.json` all live at the consuming repo's root, one level above `.agents/`. Rather than add a root-bound anchor to `Intent.Modules.Common` (forbidden without explicit sign-off — see `local-add-module-skill-template`), each of these File Templates uses `Template Settings(Role=Default)` — the app's own output root, unaffected by the `.agents` anchor entirely — with `relativeLocation` set to the target subfolder (`""` for `AGENTS.md` itself, `"../.codex"`, `"../.kiro/hooks"`, `"../.config"` measured from `.agents` would also have worked via `Role=AI.Context` plus a `".."`-escaping `relativeLocation`; both were verified to resolve to the same physical path — `Role=Default` was kept for these four templates because it needs no escape at all).
- **A settings switch that suppresses a File Template's output entirely is implemented in its registration, not its content.** The template's `...TemplateRegistration.cs` overrides `Register(ITemplateInstanceRegistry, IApplication)` (legal: the class is `Mode.Merge`, and `SingleFileTemplateRegistration.Register` is a plain `override`) and only calls `base.Register(...)` when the switch is on, read through `Intent.Modules.ModuleBuilder.AI.Workflow.Settings.ModuleSettingsExtensions.GetAIWorkflowSettings(application.Settings)`. `Module Settings Field Configuration` only varies content, so it cannot do this. `ITemplateInstanceRegistry` lives in `Intent.Registrations`, which the scaffolded stub does not import.
- **Superseded — the standalone `Intent.Agent.Gate` dotnet-tool CLI was replaced by a file-based app generated as template content.** The paragraph this replaces described `Modules/Intent.Agent.Gate/` (packaged as the `intent-agent-gate` dotnet tool, with `context`/`guard-write`/`close-out`/`doctor` commands) as complete and harness-agnostic. That design was dropped: `.NET 10`'s `#:include` directive (SDK 10.0.300+) makes a dependency-free file-based app viable, so the module now generates the gate's C# sources directly into the consuming repo's `.agents/hooks/` via a `GateScripts` File-Per-Model template, with no install step, no dotnet-tool manifest, and no `context`/`doctor` commands (dropped — `SessionStart` now only warms the build cache; a broken gate announces itself under fail-closed rather than needing a diagnostic command). `Modules/Intent.Agent.Gate/` and its `DotnetToolsJson` template were deleted. See the module's plan document (`intent/.plans/2026-09-15-steer-acp-agents-to-workflow-skills.mdx`) for the full design and the vendor-doc corrections made while implementing it (Kiro does have `SessionStart`; Codex and Kiro need `$(git rev-parse --show-toplevel)` since neither exposes a project-root env var; Cursor fails *open* on any exit code other than exactly 0 or 2, so the gate's top-level handler must call `exit(2)` explicitly rather than rely on a crash's default code).
- **Every hook file that other tools can also write to is merged, never owned: `.claude/settings.json`, `.codex/hooks.json` and `.cursor/hooks.json`.** (This replaces an entry that left `.claude/settings.json` ungenerated, and one that judged `.cursor/hooks.json` safe to own outright.) Cursor allows exactly ONE project hooks file and Codex reads one per config layer, so any other tool's hooks share the file with ours, and owning it deleted them on every Software Factory run — `codebase-memory-mcp`, for one, registers Codex hooks on this very machine. Kiro, Copilot and OpenCode each read every file in their hooks folder, so those keep files of their own. The rules live in `HookConfigMerge` (add if absent; rewrite an entry whose command EXACTLY matches one we generated, current or `Superseded`; leave anything else mentioning our gate path and subcommand alone) and what each harness registers lives in `HarnessHookSets`. Both are deliberately free of Intent dependencies so `Tests/AgentGate` compiles the real files — the earlier tests ran against a hand-ported copy of the merge, a seam a template change could slip through. Our own entry is found by command across EVERY matcher, not just the current one: Codex's matcher changed (`Write|Edit|ApplyPatch` → `apply_patch|Edit|Write`), and keying on it would have left the old entry, with its old command, running beside the new.
- **Every hook command signals through the exit code, universally: 2 blocks, 0 allows.** Claude Code, Codex, Kiro and Cursor all honour this (verified against each vendor's docs), which is what makes a single gate script portable across all four — the `--harness` flag only selects the stdout JSON *shape* for the harnesses that read one (Kiro reads none — it blocks on exit code plus stderr text alone, and on a successful exit incorporates stdout directly into the agent's context, which is why `close-out`'s warning is plain text for Kiro and JSON everywhere else). `close-out` never denies — every one of its checks is a warn, so it always exits 0 regardless of findings; only `guard-write` and `guard-version` can deny.
- **`OpenCodePlugin` (`.opencode/plugins/intent-agent-gate.ts`) was planned in the model-changes table but never actually built until it was separately caught and closed.** Built as a `tool.execute.before` hook using Node's `spawnSync` (not the `$` shell API, to avoid shell-quoting risk entirely) that throws on any non-zero gate exit - which covers fail-closed for free, since a build failure and a deny both produce non-zero and both throw. The real `input.tool`/`output.args` shape was confirmed by directly probing a real `opencode run` with a diagnostic plugin rather than assumed from docs: `input.tool` is `"write"`/`"edit"`, and critically `output.args` uses **camelCase `newString`** for the edit tool, not Claude Code's `new_string` - `StdinEditExtractor` only checked the snake_case form and was fixed to check both, with a unit test. Then verified end-to-end for real: a real `opencode` CLI run (model `openrouter/z-ai/glm-5.2`) denied a hand-edit to a real `managed-files.xml` path and left the file untouched, and allowed a legitimate edit to an unmanaged file. This is the only harness-matrix row backed by an actual run rather than documentation. See the harness matrix in `intent/.plans/2026-09-15-steer-acp-agents-to-workflow-skills.mdx`.
- **OpenCode's model identifier needs all three segments: `<configuredProviderName>/<model.id>`, and `model.id` can itself contain a slash.** For a model routed through OpenRouter, `-m openrouter/glm-5.2` and `-m z-ai/glm-5.2` both fail with `ProviderModelNotFoundError` (the first suggests the second, which then also fails) - the working form is `-m openrouter/z-ai/glm-5.2`, confirmed by reading `opencode`'s own session log (`model.id=z-ai/glm-5.2 model.providerID=openrouter`) after a manual run. `--print-logs --log-level DEBUG` surfaces this error directly instead of the opaque `UnknownError`/`Check server logs` the CLI shows by default.
- **A build failure alone is not enough to fail closed - `dotnet run` exits 1 on a broken build, not 2.** Cursor's own docs confirm any exit code other than exactly 0 or 2 is treated as an allow, so a bare `dotnet run gate.cs -- <command>` hook command would silently stop protecting anything the moment the gate's own source broke - and `Cli.cs`'s top-level try/catch cannot fix this, since it never runs until after the build already succeeded. Fixed at the hook-command level, not in C#: every generated GUARD command collapses any non-zero exit into the universal block signal. Close-out is never wrapped, and there is no single wrapper any more — see the per-harness shell decision below for which form each harness gets and why. Locked in by `Tests/AgentGate/GateSmokeTests.cs`, which runs each `GateCommands` form, against a deliberately broken gate, in the shell it is generated for. Found by writing a test for the plan's own "fail-closed" acceptance criterion, not by inspection.
- **`ManagedFilesGuard` must resolve a managed-files.xml entry's path relative to the owning application's OUTPUT ROOT, not the directory the xml file itself sits in.** Those coincide for an ordinary module (its `.application.config`'s `location` attribute is `.`), but not for an app like this repo's `ModuleBuilderAiSkills` dogfood app, whose metadata lives under `Modules/ModuleBuilderAiSkills/` while `location="..\.."` points its actual output at the repo root. Resolving relative to the xml's own directory alone silently allowed a genuinely managed path through - undetected for most of this implementation, because every earlier manual test happened to target a path where the two roots coincide. Caught by writing `GateSmokeTests` against this repo's own real managed-files.xml, not by inspection. Fixed by reading the sibling `.application.config`'s `location` attribute before resolving each entry.
- **A version like `1.0.3-pre.0` textually contains its own plain form `1.0.3` as a substring**, which broke `CloseOutAuditor`'s release-notes-heading check: the original condition was "heading contains the full `-pre` string AND does NOT contain the plain string," and the second half was always false, since `"Version 1.0.3-pre.0".Contains("Version 1.0.3")` is true. Fixed by dropping the second condition - the full `-pre` string being present in the heading is sufficient on its own to warn. Found by a failing unit test, not by inspection.
- **The Layer 1 test project could not be named `Tests/ModuleBuilderSkills/` as the plan first specified** - that path already exists as a real, separate consuming application (id `fcb00a56-0c79-4c8f-b1ed-558727e509fe`) used to test AI.Skills/AI.Workflow installation, with its own `.application.config`/`modules.config`/Codebase Structure metadata. Named `Tests/AgentGate/` instead. Neither this new project nor other real test projects in this repo (e.g. `ArchTemplateResearch.Application.UnitTests`) are registered in `Tests/Intent.Modules.Tests.sln`, which only lists two of many `Tests/` subfolders - that file is not a reliable index of what test projects exist, and was left alone rather than guessed at.
- **`ModuleVersionAuditor`'s and `CloseOutAuditor`'s change detection must include untracked files, not just `git diff --name-only HEAD`.** That command alone is blind to brand-new (never-added) files, so a module created entirely from scratch in one line of work would be invisible to every close-out check keyed on "which modules changed." Fixed by unioning it with `git ls-files --others --exclude-standard`. Found empirically by running the gate against this module's own uncommitted work, not from documentation.

- **Every hook template must write INSIDE its own anchor folder; a `relativeLocation` that escapes with `../` collapses every anchor onto one path.** The hook templates carry `Role=AI.Context`, which is a fan-out role matched by *every* AI harness anchor (`.agents`, `.claude`, `.codex`, …). A template that escaped upward to a single shared location therefore resolved to the identical path from each anchor, and the Software Factory stopped dead with `DuplicateOutputPathException`. This was patched downstream five separate times before the cause was found. The fix is structural rather than defensive: each harness gets its own nested copy (`.claude/hooks/gate/`, `.codex/hooks/gate/`, …), so a cross-product of anchors produces a cross-product of *distinct* paths and collision is impossible by construction. The anchor folder name is also the harness's identity — `OutputTarget.Name` — which replaced probing the disk for which harnesses exist.
- **Durable commentary in a template partial goes INSIDE a `Body = Mode.Ignore` method body, never above a `Mode.Fully` member.** Only the body is protected from regeneration; a comment above the member is not, and a partially removed one can still read as deliberate.
- **`ScaffoldCompatibility.cs` declares the `Intent.ModuleBuilder.Api` namespace empty, deliberately.** The `FilePerModel`/`SingleFileListModel` registration scaffolds always import it, and this module's registration model types are local marker classes, so nothing else supplies it. Referencing `Intent.Modules.ModuleBuilder` instead would force every consumer to install the whole Module Builder module for a `using` nothing consumes.
- **The gate must exempt three categories of file it would otherwise be right to block**, all discovered by the gate obstructing this module's own development: files the Software Factory MERGES into (`.claude/settings.json`), files it SCAFFOLDS and then expects to be hand-authored (`*TemplatePartial.cs`), and files it SEEDS ONCE and never rewrites (`release-notes.md`, declared `OverwriteBehaviour.OnceOff`). All three appear in `managed-files.xml` indistinguishably from owned output, and the manifest records only path and templateId — not overwrite behaviour — so the gate cannot infer any of it and has to name them explicitly. The release-notes case is the sharpest: the gate was denying the documentation chore this module itself ships and mandates.
- **Cursor has no before-file-edit hook at all.** `afterFileEdit` fires once the write has landed and cannot deny it, so a write guard placed there is advisory while appearing to enforce. The blocking hook is `preToolUse`, whose matcher takes Cursor's own tool categories (`Shell`, `Read`, `Write`, `Grep`, `Delete`, `Task`, `MCP:<name>`) — not another harness's tool names. Cursor also documents a per-entry `failClosed: true`, which covers the failure modes the `; test $? -eq 0` wrapper cannot, such as the command failing to start. This was hidden while Kiro, Cursor and Codex were arms of one template's switch, and surfaced immediately on splitting them apart.
- **`InstallAgentGateHooks()` returns false when the setting is absent or unparseable, and generates nothing, silently.** No warning, no log line, nothing in the Software Factory result — output simply does not appear. Diagnosing it in a consuming application cost most of a session and was only settled by bypassing the gate in a throwaway build; every inference from the outside was contradicted by a template that had generated once earlier and whose output had not needed to change since. A template that stopped running and one that runs and produces identical output are indistinguishable from the SF result alone.

- **Every harness's hook command reaches the gate through the same plain path relative to the project root, with no harness-specific variable.** (The rest of the command now differs per harness, because the harnesses do not share a shell — see the per-harness shell decision below.) The plain path is what each harness's own documentation uses (Cursor's reference shows `./hooks/validate-tool.sh`, Copilot's `./scripts/log-prompt.sh`), and uniformity across six harnesses is worth more here than a partial fix applied to one. An intermediate version anchored Claude Code's commands to its documented `${CLAUDE_PROJECT_DIR}` placeholder to solve the cwd hazard below; it worked, and was reverted because it left one harness spelled unlike the other five for a problem none of them can solve uniformly.
- **The cwd hazard is real, unsolved in config, and belongs in agent guidance.** A hook command runs in whatever the agent's current directory happens to be — Claude Code's docs describe it as "the new directory after Claude runs `cd`" — so if the agent leaves the project root, a relative path stops resolving and the gate cannot be found. Running a build from inside a module folder is enough; it happened three times while building this module. It fails CLOSED, so nothing is waved through, but the agent is locked out of editing until its working directory returns. Only the LOOKUP of `gate.cs` is affected: once running, the gate finds the repository root itself by walking up, so it never mistakes a subdirectory for the root and never fails open.
- **A merge-only template can never ship a correction to something it has already written.** `EnsureHook` originally just added absent entries, so the `${CLAUDE_PROJECT_DIR}` fix would have reached new installs only and every existing repository would have kept the broken command indefinitely. Fixed by having the template recognise its OWN earlier output — an exact-match list of previously generated command strings — and rewrite those in place. Exact match rather than "any command mentioning our gate path" is the whole point: the looser test would also silently overwrite a command the developer had adjusted, which this template promises never to do. Both directions are covered by tests. Now shared by all three merged files through `HookConfigMerge`; `GateCommands.Superseded` lists every earlier form, and 1.0.0-pre.9 added the `; test $? ...` wrapper every harness used up to pre.8.
- **`guard-version` and `close-out`'s module resolution assumed every module lives under a top-level `Modules/` folder, with its `.imodspec` beside its `.application.config` — both wrong outside this monorepo.** Found via an adversarial OpenCode test run against a real consumer solution built from the Application Template Builder, where `location=".."` splits an application's metadata folder from its real output root. `ModuleResolver.FindModuleFolderByApplicationId`, `ModuleVersionAuditor` and `CloseOutAuditor` each independently hardcoded `Path.Combine(repoRoot, "Modules")` — this is exactly the same disease line 42 above already fixed once, in the now-deleted `ManagedFilesGuard`, and never ported to these three. Replaced with one shared `ModuleDiscovery` (in `GitSupport.cs`, since it needs the same git-invocation infrastructure): finds every `*.application.config` in the repo via `git ls-files` (tracked and untracked, so a module created moments ago is still found), reads each one's `location` attribute to resolve its real output root, and locates `.imodspec` there — bounded to the root itself and one level of subfolders (never an unbounded recursive search), because an application whose output root is an ancestor of many unrelated modules (this repo's own dogfood app, output-rooted at the repository root) must correctly report "not a module" rather than picking up an arbitrary descendant's imodspec. `git ls-files` failing for any reason (not on PATH, not a git repository) falls back to a bounded filesystem walk skipping `.git`/`bin`/`obj`/`node_modules` — never silently to "no modules found". Covered by `GuardVersionTests` fixtures using a non-"Modules/" folder name and a split metadata/output-root layout, neither of which the old code could resolve. The one-folder-deeper search then produced a false positive of its own: an application whose output root is `Tests/` claimed `Tests/ModuleBuilders/ModuleBuilders.imodspec` and close-out warned about a module called "Tests". A subfolder carrying its own `.application.config` is now skipped, since it is a different application's module; covered by `CloseOutTests.Does_not_treat_an_ancestor_application_as_the_module_beneath_it`.
- **Outside a git repository the gate roots itself at the folder the hook runs from, rather than giving up.** The filesystem fallback added with the discovery fix only ever covered git failing inside a repository. `Cli.Run` still returned "no opinion" whenever no `.git` existed above the working directory, so a folder that hadn't been `git init`-ed had no protection at all: metadata edits and version downgrades were both allowed. Found by an adversarial run from a scratch folder in `%TEMP%`, after this module's own release notes had already claimed the case was handled. guard-write never needed a repository root (its checks are path patterns), and guard-version's discovery already falls back to a filesystem walk once git fails, so the fix is the root fallback alone. What genuinely needs git degrades quietly: close-out finds no changes and stays silent, and the double-bump check has no HEAD to compare against. Covered by the two `*_outside_a_git_repository` tests, which run under `%TEMP%` with no `.git` and the real git process. The fallback immediately exposed a latent deadlock: `GitProcess.Run` redirected git's stderr but never read it, and outside a repository `git diff HEAD` writes a ~7 KB usage dump there, enough to fill the pipe. git blocked writing, the gate blocked waiting for git, and close-out never returned, which hangs the agent. It had been unreachable before only because close-out bailed out without a repository root. Stderr stays redirected (it must not leak into the hook's stderr, which harnesses show to the agent) but is now drained concurrently. **Any process this gate starts with a redirected stream must drain every redirected stream.** Found by the adversarial run, not by the suite: every earlier test either used the fake git provider or hit git calls whose stderr was a one-line error. `CloseOutTests.Finishes_silently_outside_a_git_repository` now bounds the call to 30 seconds so a regression fails instead of hanging.
- **OpenCode's plugin discovery is anchored to launch cwd, not the git repository root — confirmed by a live experiment, not assumed.** A session launched with cwd at the git root failed to load a plugin sitting one folder below; the same plugin, copied to a fresh process launched with cwd at that folder, loaded correctly (`opencode debug config` showing `scope: "local"`). This is not a defect in this module — it is the same "launch the harness rooted at the application's own output folder" requirement every other harness already needs, just manifesting as a silent no-load instead of a failed relative path. No code change follows from it. Where launching at the right cwd is not possible, `OPENCODE_CONFIG_DIR` (documented, confirmed working) points OpenCode at the correct `.opencode` folder explicitly.

- **guard-write protects Intent's METADATA, not its generated OUTPUT - and the difference is the single most consequential decision in this module.** The original instruction was that `managed-files.xml` must not be touched; that was implemented as "nothing LISTED IN managed-files.xml may be touched", which is close to the opposite rule. Under the wrong scope the guard permitted every file it should have protected - `*.application.config`, `*.application.managed-files.xml`, designer XML under `Intent.Metadata/`, anything under `.intent/` - while blocking authoring a scaffolded template, writing release notes and correcting a `.csproj` package version. Across a full session of real use it produced five false positives and not one true positive. Metadata is the right target because it is high precision by construction: every legitimate change has a proper mechanism (the Intent MCP server, or a skill that drives it), so a denial can always say where to go instead of merely saying no. Editing generated output, by contrast, is usually just futile rather than harmful, and is frequently the intended workflow.
- **The three exemption lists are gone, and their absence is the point.** `MergeOwnedSuffixes`, `CoOwnedScaffoldTemplateIdPrefixes` and `SeededOnceTemplateIds` each existed to carve a category of hand-authored file back out of the over-broad rule, and each was discovered only by the gate blocking real work. A rule needing a growing list of exceptions found by being wrong in production is the signal that the rule is aimed at the wrong thing.
- **`.github` is the one anchor this module does not own.** Every other harness folder exists solely for that tool; `.github` already holds workflows, issue templates and CODEOWNERS in most repositories. The Copilot template therefore owns `.github/hooks/` and nothing above it, and its config file is named `intent-agent-gate.json` rather than `hooks.json` because Copilot treats every `*.json` in that folder as a hook file - an unrelated one may well be sitting beside it.
- **`Use Pre-release Versions` reaches the gate by being baked into the generated gate source (the `Cli` part of `gate.cs`), not through a `--scheme` flag on each hook command.** The flag design meant six hook configs each had to carry the setting, and only OpenCode's ever did — the other five ran `guard-version` under the `final` default, so the pre-release rule was silently unenforced there while the skill text still told the agent to use `-pre`. `GateScripts.GetModels` now rewrites Cli.cs's `DefaultScheme` constant from the setting, and every hook command (OpenCode's included) is spelled without the flag. Rejected: adding the flag to `GateCommands.Guard()`, because `.claude/settings.json` is merge-owned and every old command form would have needed a `Superseded` entry to reach existing installs; baking it in changes no command string at all. An explicit `--scheme pre|final` still overrides — `final` had to be made parseable for that, since the old parser only recognised `pre`. `WithDefaultScheme` throws if the constant's line ever stops matching, so a refactor of Cli.cs cannot silently fall back to `final`.
- **Known gap: no `.cursor` anchor is modelled in this repo's dogfood app or in the Application Template, so an application scaffolded from either gets no Cursor hooks.** The Cursor templates themselves work (the test app, which does model `.cursor`, generates them); the gap is purely that the anchor folder is absent from what new applications start with. Accepted for now rather than fixed, pending a wider decision on how these bundles get introduced into applications at all.
- **Known gap: when an application's output root sits below the folder the harness is launched from, no hook fires at all.** Every harness loads its hook config only from its launch folder, and this module writes those configs under each application's own output root. In a solution scaffolded by the Application Template Builder, such as `E:\Workspace\ModuleBuilderAiWorkflowTest`, where NewModule outputs to `NewModule\` and the metadata app to `intent\`, a harness launched from the repository root (the natural place to work) loads no gate: a live write to a protected path went straight through. The gate logic itself passed every check when invoked directly. This generalises the OpenCode cwd finding above to every harness. Closing it would mean generating hook configs at the launch root, which needs a root-bound anchor, and that is forbidden without explicit sign-off (see the root-anchor decision above). Deferred to the wider distribution decision.
- **The gate is ONE generated `gate.cs`, because `#:include` needs SDK 10.0.300+.** A colleague on SDK 10.0.102 got `Unrecognized directive 'include'` on every guarded edit and every Stop, with nothing saying why; SDK 9 says `Couldn't find a project to run`. `GateScripts.ComposeGate` keeps the sources as separate constants in the module and joins them on output: leading `using`s hoisted and de-duplicated, each file-scoped namespace folded into one block-scoped `namespace Intent.Agent.Gate { }` (C# rejects a file-scoped namespace after top-level statements, CS8956), a `#!/usr/bin/env dotnet` first line (which also silences CA2266 on every warm), and the entry point behind `#if !AGENT_GATE_TESTS`. `Tests/AgentGate` compiles that same file with `AGENT_GATE_TESTS` defined and `<Features>FileBasedProgram</Features>`, without which a project rejects the `#!`/`#:` lines (CS9314/CS9298). Verified to compile and guard correctly on SDK 10.0.100 and 10.0.401.
- **Harnesses do not share a shell, so each gets the command form its shell can run — measured on Windows by driving each harness for real, not taken from docs (which mostly do not say).** Claude Code runs hooks in Git Bash (PowerShell only if Git Bash is absent). Codex runs `command` in a POSIX shell and `commandWindows` in PowerShell, not cmd. Copilot runs its `powershell` key in PowerShell 7. Kiro CLI runs hooks in PowerShell. On macOS/Linux everything is POSIX. So `GateCommands` has: `GuardPosix` (`... || exit 2`), `GuardPowerShell` (`...; if ($LASTEXITCODE -ne 0) { exit 2 }`) for fields only PowerShell runs, `GuardPortable` (`...; exit $LASTEXITCODE`) for Cursor and Kiro, which have one command string and no per-OS field, and `CloseOut`, never wrapped. Two measured surprises drove the forms. PowerShell hands a native exit 2 back as 1, and Kiro treats 1 as "hook failed, proceed" — a real deny let the protected write through until `; exit $LASTEXITCODE` restored the 2 (bash expands the empty variable, so `exit` keeps the gate's own code); this is very likely Kiro's open issue #8264. And Copilot also runs every hook in `.claude/settings.json`: under PowerShell the old `; test $? -eq 0 && exit 0 || exit 2` failed, and Copilot denies on a failed hook, so it blocked EVERY write in a repo carrying both folders. `... || exit 2` behaves identically in bash and allows correctly under PowerShell 7. Rejected: generated `gate.sh`/`gate.ps1` launchers, because Claude Code, Cursor and Kiro offer no per-OS field to choose between them; registering a bash and a PowerShell command side by side, because bash exits 2 on a syntax error and every harness runs all registered hooks, so the PowerShell copy would block everything on macOS/Linux; and a cmd-form `commandWindows` (`|| exit /b 2`), proposed first and wrong because Codex uses PowerShell there. Kiro alone still lets an action through when dotnet itself cannot run — it has no fail-closed mechanism — and that is accepted.
- **close-out never blocks, crash included.** A Stop hook exiting 2 tells Claude Code and Codex the agent must keep going, so the old wrapped close-out turned a gate that could not build into an endless loop of turns — observed: the colleague's agent re-reported "nothing to close out" turn after turn. Its command is never wrapped, and `Cli.Run` now catches a close-out crash separately and exits 0 with a note on stderr; the guards still exit 2 on a crash (`FailClosedTests` covers both).
- **Codex edits arrive as `apply_patch` text, and the guard reads them.** The payload is `tool_input.command` holding the patch, with paths only on `*** Add File:` / `*** Update File:` / `*** Delete File:` / `*** Move to:` lines — no `file_path`. The gate used to find no path, say "no opinion" and allow every Codex edit, on every OS, unnoticed until Codex was driven for real. `ApplyPatchExtractor` returns every touched path (a move's destination included) plus the lines each adds, so the `.imodspec` `<summary>`/`<description>` rule applies to patches too. It finds the patch by content (`*** Begin Patch`), not by key, so a renamed field does not quietly switch the guard off.
- **Kiro's `.kiro/hooks/*.json` is read by the Kiro IDE and by Kiro CLI v3 in interactive sessions only.** Per Kiro's docs and confirmed on CLI 2.22: the default v2 engine reads hooks only from agent configs and ignores the file, and `kiro-cli --v3 chat --no-interactive` never loads workspace hooks (Kiro issue #11598), so it cannot be tested headlessly. Generating a v2 agent config was rejected — it creates an agent users must select with `--agent`, for an engine Kiro is replacing. The write matcher lists every known write-tool name (`write|fs_write|fsWrite|str_replace|fs_append|delete_file`) because v3 renamed and split tools and the docs do not say whether matchers see aliases; it is still UNVERIFIED under v3, and `.*` was rejected because read tools carry a path too and the guard would deny reading metadata. Updated 2026-10-08: Kiro's headless docs now say CLI 2.27.1 and later load workspace hooks in v3 non-interactive runs (Kiro issue #11598 closed), and 2.28.0 added category-based hook matching. Run for real on 2.28.0 (headless, v3): the hooks fire, and the existing matcher catches `str_replace`. Two things the gate had wrong surfaced at once. Kiro CLI v3 runs the hook command in `cmd.exe`, not PowerShell, so the portable form's `; exit $LASTEXITCODE` arrived as arguments (`kiro;`, `exit`, `$LASTEXITCODE`) — the gate read harness `kiro;` and answered in the wrong shape; and its edits carry `newStr`, which the gate did not read, so a `<summary>` edit went through. The command form was kept, because the Kiro IDE still runs hooks in PowerShell where the tail is needed (exit 2 otherwise arrives as 1); instead `Cli.WithoutShellTail` drops everything from the first argument ending in `;`, and cmd.exe passes the gate's exit code through unchanged. `newStr` and `fileText` are now read. Both fixes are unit-tested and confirmed on Kiro CLI 2.28: a `<summary>` edit is denied (exit 2 through cmd.exe blocks the write), and a valid version edit lands with the reminder on stdout.
- **Setup failures are explained to the agent in the generated workflow instructions, not by the gate.** When the hook cannot run at all, the gate's own code never executes, so only `dotnet`'s text reaches the agent. `ModuleBuildingWorkflowMd` therefore carries an "If An Agent Gate Hook Itself Fails" section, only when `Install Agent Gate Hooks` is on, mapping each raw error to its fix and telling the agent not to retry or work around it. Chosen over launcher scripts because instructions work identically on every OS and harness.

- **`module-context-capture` excludes Intent Architect platform problems from `CONTEXT.md` and routes them to the user for Intent support.** Decided by Dandré: a platform defect recorded as module context becomes a permanent, unreported workaround, and later sessions read it as a deliberate constraint of the module. The skill's "What Stays Out" list points to a dedicated section and a checklist item. The single exception, also Dandré's: a genuine limitation of the Intent API or SDK (something it does not offer, as opposed to something that malfunctions) is recorded together with the module decision it forced; when unsure which it is, the agent treats it as a defect and reports it. This module's own `CONTEXT.md` was brought into line at the same time: entries describing platform defects (module-cache staleness, Software Factory output-tracking and formatter defects, Template Outputs on reinstall) were removed, and entries mixing a limitation with a decision were rewritten around the decision.
- **`module-context-capture` tracks dependency version contracts — the modules this one depends on, not its own contract.** Requested by Dandré: when a dependency's interface changes between versions (1.0 has one shape, 2.0 another), the code says nothing about which version it was written for or what the older form was. The skill records the targeted version, what changed in which version, how the module adapted and why the floor is where it is, and tells the reader to compare recorded versions against the current reference before trusting them. Recording this module's OWN contract changes for its dependents was offered and declined; only the dependency direction is covered. An Intent module or SDK interface change between versions counts as a contract change, so it is recorded despite the no-Intent-defects rule above.

- **The generated hooks, instructions and skills are evaluated by an agent eval suite at `Tests/AgentEvals/`, internal to this repo.** Dandré's framing: one process spawns each AI harness as a test subject, gives it tasks that should make the hooks and guidance matter, and rates how well they worked. Decided with him: a deterministic conductor runs everything and makes the hard pass/fail checks, and a judge model scores only the qualitative dimensions (Steered, Communicated) against a fixed brief, quoting evidence; judge scores never decide a pass. Rejected: an AI harness as conductor (least repeatable, and it judges with whatever model it runs on), and Intent's own agent as conductor (ties every run to Intent being open). The conductor is a .NET file-based app (Dandré's choice; it needs SDK 10.0.300+ for `#:include`, acceptable because it never ships). Three layers: static wiring checks (is each artifact where the harness loads it), hook scenarios, and guidance-use scenarios. The suite evaluates what `Tests/ModuleBuilderSkills` has generated, so that app must be regenerated after a module change before a run means anything.
- **The eval suite writes only under one root it owns, outside the repo (`%LOCALAPPDATA%\IntentAgentEvals`), and prunes it itself.** Dandré rejected the first version's spread - sandboxes in `%TEMP%`, reports in the repo, a harness home in the user profile - and any cleanup by hand. Chosen over Docker containers (kept as a later addition for Linux) and over adopting Inspect AI or promptfoo: those test one step removed from what users run, lose the real Windows shells where the original gate bugs lived, and route model calls off the Claude subscription. Harness isolation follows from what each CLI allows: Claude Code via `--setting-sources project,local` and `--strict-mcp-config`; Codex via its own `CODEX_HOME`, because `--ignore-user-config` also stops Codex loading any project hooks (codex-cli 0.155) and a loaded user config gets a trust entry written per workspace; OpenCode via XDG folders; Copilot via `COPILOT_HOME`.
- **Designer-route scenarios use a stub Intent MCP server that applies simple scripts.** It exposes `run_designer_script` under the real name so `guard-version` fires on it as on the real server. It must apply a `setProperty` script's change: an early stub that reported success while changing nothing provoked the agent into a shell workaround - the very behaviour under test - so the stub logs what it wrote and checks count only changes made some other way.
- **`INTENT_GATE_LOG` exists for the eval suite.** Each harness reports hook activity differently, if at all, so the gate itself records every run (command, exit code, duration, stdin/stdout/stderr, truncated) when the variable names a file. It is off by default, never changes a verdict (failures swallowed, a colliding append retried then dropped), and buffers the command's output only while logging is on. The suite writes the log outside the workspace so it never appears in the agent's diff.

- **A hand-edited `.imodspec` `<version>` is held to the same rules as the designer route, through one shared `VersionRules`.** The version rules used to guard only `run_designer_script`, and every version change in the eval runs was a hand-edit, so in practice they guarded nothing. Dandré's call: the agent may edit `<version>`, but must be reminded to load `module-version-increment` first. So guard-write reads the version an edit writes (whole file, Edit snippet or `apply_patch` added lines) and denies an invalid one (a second bump against HEAD, a bare release under `Use Pre-release Versions`, an unparseable version) with the skill pointer; a valid one is allowed with the reminder as `additionalContext` (Claude Code, Codex) or plain stdout (Kiro). A downgrade stays allowed on this route only: the Software Factory will not write a lower version from the designer, so the hand-edit is the sanctioned way to correct an over-bump. Rejected: denying every hand-edit and forcing the designer route — it would have blocked that sanctioned correction.
- **The gate never writes an "allow" decision.** Claude Code treats `permissionDecision: "allow"` as pre-approval and skips its own permission prompt, so the "no opinion" notes the gate used to emit as allow decisions were quietly widening what the agent could do, and on Copilot (which ran the guard on every tool) they also put a note into the context on every call. Allowed actions now exit 0 with nothing on stdout; diagnostic notes go to stderr, which the harnesses keep out of the agent's context on success and the gate log keeps. The only stdout on an allow is the version reminder, which carries no permission decision.
- **Copilot gets one pre-tool hook, `guard-tool`, which dispatches by tool name, behind a matcher.** Copilot's own hook files send camelCase `toolName`/`toolArgs` (observed as an object; documented as a JSON string, so both are accepted), with its own names (`edit`, `create`, `view`) and fields (`path`, `new_str`, `file_text`). `HookPayload.Normalize` rewrites that into the `tool_name`/`tool_input` shape every extractor reads — without it the `<summary>` guard read no content and allowed every Copilot edit. The matcher (`create|edit|str_replace_editor|apply_patch|write|.*run_designer_script.*`) keeps the gate off unrelated tools; the dispatch keeps it correct where a matcher is ignored, and a read-only tool list stops a `view` of metadata being denied like an edit (an unknown tool counts as a write, so a new tool fails closed). Rejected: two hooks (write and version) — without a working matcher both would run on every tool call.
- **Claude Code's copy of the gate steps aside when Copilot runs it, decided by two signals that must agree.** Copilot CLI (and Cursor, with third-party hooks on) also runs `.claude/settings.json`, so every guarded action reached the gate twice. Probed with one Copilot run logging each hook's environment and process tree: environment variables are useless — the eval runner was started from a Claude Code session and every `CLAUDE*` variable was inherited by Copilot's hooks, and Copilot itself sets `CLAUDE_PROJECT_DIR` for Claude-format hooks — but the process tree is clear (`pwsh ← copilot` versus `bash ← claude`). The copy steps aside only when the nearest harness ancestor is Copilot or Cursor AND, for a guard, the payload lacks `transcript_path`, which Claude Code always sends and Copilot's Claude-format payload does not. The second signal covers Claude Code started from inside a Copilot session, where the tree alone would switch Claude's guard off. Cursor's payload carries `transcript_path`, so under Cursor both copies still run — documented, not engineered, per Dandré. A harness's own hook file never steps aside: only the `claude` id is ever subject to it.
- **The gate is no longer generated into `.agents`.** `GateScripts` fanned out to every AI.Context anchor, including `.agents`, but no harness loads hooks from `.agents` (checked against each vendor's hook documentation), and Intent Architect's own agent runs the real harnesses through ACP connectors (Claude Code, Codex, Copilot, OpenCode), each loading hooks from its own folder. The copy was never executed. `GateCommands.HookedHarnessFolders` now names the folders that carry a hook configuration, and the template declines every other anchor. `Tests/AgentGate` compiles the `.claude` copy instead.
- **The workflow instructions reach every harness from a harness-owned location, never a root-level file.** Dandré ruled out `AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md` and the like. Researched per vendor (2026-10-08): Claude Code `.claude/rules`; Copilot CLI `.github/instructions/*.instructions.md` with `applyTo: '**'` (it also reads `.claude/rules`, undocumented, so both load where both exist); Cursor `.cursor/rules/*.mdc` with `alwaysApply: true` — a plain `.md` there is ignored, so `ModuleBuildingWorkflowMd` switches extension when its anchor sits under `.cursor`; Kiro `.kiro/steering` (`inclusion: always`); OpenCode only through the `instructions` list of an `opencode.json`, which it also reads from `.opencode/` — `OpenCodeInstructionsConfig` merges a glob per instructions folder into it; Codex only through `developer_instructions` in `config.toml` — `CodexInstructionsConfig` writes the workflow text into a marked block there. One file carries every harness's always-on switch in its frontmatter (`applyTo`, `alwaysApply`, `inclusion`). Rejected for Codex: `model_instructions_file` (replaces Codex's own base instructions) and `project_doc_fallback_filenames` (bare file names, not paths). Kiro reads skills only from `.kiro/skills`, so it needs an `AI.Context.Skills` anchor there.
- **Instruction and skill locations are the consuming application's to model, not this module's.** Both templates follow the `AI.Context.Instructions` / `AI.Context.Skills` anchors in the consumer's Codebase Structure, so a harness only gets the workflow where its folder is modelled — `Tests/ModuleBuilderSkills` now models `.github/instructions`, `.cursor/rules`, `.kiro/steering` and `.kiro/skills`. The two config templates are anchored on the harness folder itself and decline when there is nothing to point at.
- **OpenCode's close-out runs when the session goes idle and reports to the person.** OpenCode has no stop hook; the plugin listens to `session.status` with status `idle` and to the deprecated, still-published `session.idle`, dropping a second notice within three seconds. The warning goes to OpenCode's log and a toast — like Claude Code's `systemMessage`, it informs the person. Rejected: `client.session.prompt`, which would put it in front of the agent but start another turn.
- **Shell writes are a known, accepted gap.** Hooks see file-edit tools and MCP calls; a shell command that writes metadata or a version goes around the gate, and agents do this, mostly after a denial. Dandré's call: document it, do not try to block it — parsing arbitrary shell commands for writes would be unreliable and produce false positives.
- **Verified on Windows only.** Every eval run behind these decisions ran on Windows; the POSIX command forms follow vendor docs but are untested.

## Invariants & Constraints

- A conditional section interpolated into `ModuleBuildingWorkflowMd` must end with a blank line before the next `===` separator. A `===` line directly under a paragraph is a Markdown setext heading underline, so the section's last sentence silently renders as a top-level heading — caught in the first regeneration of the gate-failure section.

- `AIWorkflowSettings` accessors (`UsePreReleaseVersions`, `MaintainModuleREADME`, `MaintainModuleIcon`) are generated from `Module Settings Field Configuration` children of the `AI Workflow Settings` element — never hand-edit `Settings/ModuleSettingsExtensions.cs`; add the field in the designer and regenerate.
- `module-docs-chore`'s conditional sections (`readme*`, `icon*` variable pairs) all follow the same three-part shape: a table row, a full section, a checklist item, each toggled by the same boolean. A new conditional artifact should follow this exact shape rather than inventing a different one.

## Module Interactions

- **Intent.ModuleBuilder.AI.Skills** — see the "No package dependency" and soft-reference decisions above. `module-svg-icon` there owns the actual SVG-crafting mechanics; this module only decides _when_ to invoke it and _where to source its input description_ (the module's own `.imodspec` summary/tags or `CONTEXT.md` Purpose section) — it does not duplicate the crafting guidance.

## Superseded

- **`CLAUDE_SETUP.md` and its manual-paste instructions.** Claude Code's hook configuration was originally left to the developer to paste in, because no way had been found to merge into `.claude/settings.json` without risking their own permissions, environment and unrelated hooks. `ClaudeSettings` now generates it by merging — absent entries added, existing ones never overwritten, an unparseable file left byte-for-byte with a warning rather than throwing and failing the consumer's whole run. The reversal rests on tests covering each of those cases, not on optimism. `CLAUDE_SETUP.md` and its template are deleted.
- **One shared gate at `.agents/hooks/gate.cs`.** Replaced by a self-contained copy nested inside each harness folder — see the anchor cross-product decision above. Duplication is deliberate: it is what makes the collision impossible and keeps each harness from reaching into another's directory.
- **The `Target Claude Code` / `Target Cursor` / `Target Codex` / `Target Kiro` settings.** Which harnesses are targeted is no longer a set of module settings; it follows from which harness anchor folders exist in the consuming repo, with each template declining any folder it does not serve. `Install Agent Gate Hooks` remains as the single on/off switch.
- **A multi-file gate joined with `#:include`.** Replaced in 1.0.0-pre.9 by one composed `gate.cs`, because `#:include` raised the SDK floor to 10.0.300 and failed on older .NET 10 SDKs with an error that said nothing about the gate. The old per-concern files (`Cli.cs`, `SemVer.cs`, ...) are deleted from consumers on regeneration.
- **One shared `; test $? -eq 0 && exit 0 || exit 2` wrapper on every hook command, close-out included.** POSIX-only, so it misbehaved wherever a harness runs PowerShell, and on close-out it trapped agents in a Stop loop. Replaced by the per-harness forms in `GateCommands`, with close-out never wrapped.
- **Kiro and Cursor as arms of `HooksJson`'s switch.** One template owning four unrelated file shapes hid a real defect (Cursor's non-blocking write guard). Each now has its own template; `HooksJson` remains the generic template for harnesses that follow the `hooks.json` convention, currently only Codex.
