# Context: Intent.Modelers.Types.ServiceProxies

## Purpose

Defines the `Service Proxy` element type and its `Operation` / `Parameter` children, and adds them to the Services designer. A proxy maps to another application's HTTP-exposed endpoints and keeps its parameters in sync with them.

## Architectural Decisions

- **Two designer settings, with different jobs.** `Service Proxy Types` holds the element _definitions_. Its `.designer.settings` is installed with no `target` and `Extend Designers` empty, so it reaches the Services designer only through the Designer Reference from `Service Proxy Services Extension`. `Service Proxy Services Extension` is the one installed with `target="Services"`, and it extends the Services designer directly.
- **Context-menu entry points live in `Service Proxy Services Extension`** (5.5.7). The Services package option and the Diagram option are both defined there. The 5.5.4 package option was defined as a Package Extension in `Service Proxy Types` and never appeared in the Services designer. It was moved, not duplicated: keeping both would show the option twice if the referenced one ever did surface. Other modules that add Services-package menus (CQRS, Domain Events) follow the same pattern.
  - Exception: `Folder Extensions` still lives in `Service Proxy Types` and does work through the reference. It was left there to keep the change minimal. Put new menu options in `Service Proxy Services Extension` anyway.
- **Hidden "type registration" Element Creation Option.** Each package or folder extension that creates a Service Proxy with a script also carries a creation option whose visibility function returns `false`. Without it, Service Proxy is not an accepted child type of that container, and `createElement` fails.
- **Operations are unique by mapped endpoint, not by name** (5.5.8). `Name Must Be Unique` was turned on for `Operation` in 5.4.0, in a sweep across modules, with no proxy-specific reason. No .NET generator in Intent.Modules.NET uses the Operation's own name: generated client methods are named after the mapped endpoint. What breaks generation there is two Operations in one proxy mapped to the same endpoint, which hits `ToDictionary` / `.Single(...)` and throws. The name rule didn't prevent that, and it blocked a real case: two `GetById` queries from different folders of the target application. So `Name Must Be Unique` is off on `Operation`, and its Validate Function errors when a sibling Operation maps to the same element.
  - `Service Proxy` and `Parameter` keep `Name Must Be Unique`: proxy names become class names and `HttpClients:{Name}` config keys.
  - Unmapped Operations are not checked. They cannot collide on an endpoint, and an error for them was rejected in 5.5.7 (see Invariants).
  - The only code in this repo that matched on an Operation's name, the ProxyInteractions "create from proxy" macros, was changed in the same line of work (ProxyInteractions 1.1.8) to match by `Perform Invocation`.
  - Intent.Modules.Web's TypeScript/Angular generators were not checked for a dependency on the Operation name. Confirm that before releasing 5.5.8 as final.
- **Diagram creation targets the diagram's owner container** (`getCurrentDiagram().getOwner().getParent()`), not the folder of the visuals under the cursor. This matches the DomainInteractions CRUD diagram options.

## Invariants & Constraints

- The New Service Proxy creation script is duplicated inline on the Folder option, the Services package option, the Diagram option (with an extra layout step) and `Service Proxies Package`. A fix to one must be applied to all four. Moving it to a shared designer `Script` was deferred as out of scope for 5.5.7.
- `launchMappingDialog` is followed by deleting the proxy if nothing was mapped, so cancelling leaves nothing behind. The diagram variant then skips placing the visual.
- **A Proxy `Operation` can exist without a mapping.** `Operation` has `allowMapping=false`; it is only mapped when the proxy's Service Reference mapping creates it. But **New Operation** is still offered on a Service Proxy, and since 5.5.6 agents can create Operations through MCP without any dialog. The parameter-sync script must therefore tolerate `getMapping() == null` (and a mapping whose endpoint was deleted). Before 5.5.8-pre.0 it did not, and one such Operation aborted the whole `On Loaded` loop, leaving every later proxy unsynced.
  - It warns rather than skipping silently, because the warning is the only place the offending Operation gets named. This matches the existing "Http Settings not found" warning in the same script.
  - Hiding **New Operation**, or adding a validation error on unmapped Operations, was considered and not done in 5.5.7. It changes the modelling experience, and an MCP-created Operation would still need the guard.
- **The parameter-sync script has three live copies.** Here it is in `Service Package Extension` `On Loaded` and `Service Proxy Extension` `On Changed`, both in `Service Proxy Services Extension`. The third is `On Changed` in Intent.Modelers.UI.ServiceProxies. A fix to one must be applied to all three. The source is `DesignerMacros/src/service-proxies/manage-parameters/services-proxies-manage-parameters.ts`, but the embedded copies have drifted from it. For example, they call `setName(name)` where the source has `setName(name, false)`, and the UI copy creates Parameters by type id. So the 5.5.7 fix was a targeted edit to each copy and the source, not a recompile-and-paste, which would have carried unrelated changes along.
  - Intent.Modelers.ServiceProxies still has a stale `modelers/Service Proxies Core Types.designer.settings` with an old copy. Its `.imodspec` doesn't install it (left over from the 5.2.3 move into this module), so it is not a live copy.
