# Context: Intent.ModuleBuilder.AI.Skills

## Purpose

Bundles a fixed set of AI agent skills and instruction files for building Intent Architect modules into the consuming repo's `.agents/` folder. Every bundled file is generated from this module's own source and always overwritten on install/update — there is no per-repo customization, no designer model dependency for consumers, and no settings gating which skills are included.

## Architectural Decisions

- **A module's package icon is not a model-scriptable property.** Checked the `Module Settings` stereotype on `Intent Module` (properties: Version, API Namespace, NuGet Package Id/Version, Include in Module, Reference in [Designer], Include Release Notes, Project URL) and the package element itself — neither carries an `Icon` field. `Version` **is** model-owned; `Description` is **not** — it comes from the application's own description (set on the Application Settings page), exactly like the icon, so only `Version` is the contrast that holds. The icon instead lives in the module's own `.application.config`, as a root-level, attribute-less `<icon>data:image/svg+xml;base64,...</icon>` element with a sibling `<iconType>UrlImagePath</iconType>`. `.imodspec`'s `<iconUrl>` is generated FROM that value by the Software Factory on the next run — the same trap as `<version>`, just via a different source file.

- **`module-svg-icon` is a scoped, deliberate exception to "never hand-edit `.application.config`."** That file is otherwise off-limits because it is large and mostly generated. The exception is narrowed to exactly the root `<icon>`/`<iconType>` pair — never the many other `<icon type="..." source="...">` entries elsewhere in the same file, which configure unrelated per-designer-element icons.

- **The edit must be done by a script, never by `read_file`/`patch_file` on the base64 value itself.** This is a non-functional constraint, not a permissions one: the icon's base64 payload commonly runs into tens of thousands of characters. Passing it through the AI's own context is wasteful and risks a silent transcription error that corrupts the icon. The skill's script reads the drafted SVG file, computes the base64 itself, and writes the substitution directly — the AI never sees or reproduces the encoded string.

- **Default SVG house style is baked into the skill, not left open-ended.** Derived from real `<iconUrl>`/`<icon>` values already shipping in installed modules: `viewBox="0 0 50 50"`, a full-bleed circular badge, a gradient (or flat) fill in one hue family, and a single simple white glyph. Giving the AI a concrete default (deviate only when the supplied description clearly calls for it) keeps output consistent with the existing module gallery instead of reinventing a style per module. Since 1.0.4-pre.1 the style is backed by measured legibility rules (see the next entry), and one darker accent from the gradient's own hue family is allowed inside the glyph; the old "gradient plus white glyph, nothing else" read as forbidding it.

- **Never edit a `...TemplatePartial.cs` markdown raw string with Intent's `patch_file`.** The tool auto-adjusts indentation to the surrounding C#, and because the markdown lives inside a raw string literal at column 0 it re-indents the _entire_ string to the constructor's nesting level and flattens the relative indentation inside every fenced code sample. The damage is whole-file, not local to the patch, and it is silent — the tool reports success and only a non-zero `indentDelta` in the result hints at it. Use a plain text editor that does no reformatting. This was hit and reverted while adding the cross-module-integration content in 1.0.1-pre.1.

- **Flattened `Skills/{SkillName}/` into `Skills/` directly (1.0.1-pre.3).** The per-skill subfolder existed only to disambiguate the repeated `SkillMd_Agents` name across skills — the `Skills/` folder already provided that grouping, so the extra nesting was pure ceremony. Flattening, plus renaming each template with its former folder name as a prefix, removes the redundant folder while keeping every element name unique. Also caught mid-flatten: the Software Factory's rename-detection is not reliable across a simultaneous namespace + physical-path change — on at least one sibling module it silently reset a hand-authored `TemplatePartial.cs` body to placeholder content instead of preserving it (`get_file_diffs` caught it before it was applied). Treat every such rename's `get_file_diffs` output as unverified until read, not just "rename" vs "create" in the change summary.
- **`Default Location` replaced by the `MarkdownFile` constructor's `relativeLocation` argument (1.0.1-pre.3).** Discovered that `Default Location` only seeds the constructor's output-path argument at the moment a File Template element is first created; afterward the constructor's `Body = Mode.Ignore` means the model setting is never read again, so it looked live but did nothing on every subsequent regeneration. Baking the value directly into the constructor removes that dead, misleading setting. Existing consuming applications that installed an earlier version still show the old nested `Skills/{SkillName}/` shape in their own `Codebase Structure` designer until they update through the `Version Migration` added alongside this change.

- **The no-new-`.imod` diagnosis is filed as a build gotcha.** Building a module compiles its
  `.csproj`, and the packaging step that produces the `.imod` runs off that compilation — so a
  change confined to non-C# files may not trigger it, leaving templates generating from previously
  packaged content with nothing reported. `dotnet build --no-incremental` forces it. It belongs in
  `known-build-gotchas` rather than a versioning skill because it reaches every session through an
  `applyTo: '**'` instruction file, and because it is the diagnosis behind `AI.Workflow`'s "a
  version number is not a debugging tool" rule rather than a versioning decision itself.
- **Editing these raw-string templates: the closing delimiter's indentation is load-bearing.**
  `KnownBuildGotchasMd` indents its content 10 spaces and closes at the same indent, which is what
  de-indents the emitted markdown. A programmatic splice that leaves the closing delimiter at
  column 0 compiles and packages perfectly while generating an effectively empty document — caught
  only by reading the staged diff before applying (it showed every section being deleted). Always
  diff before apply on these templates.

- **`.imodspec` is merged, not regenerated — and the skills used to say the opposite.** `IModSpecTemplate` reads the existing file and rewrites six things (`<id>`, `<summary>`, `<description>`, `<iconUrl>`, `<migrations>`, `<moduleSettings>` bodies); everything else it never writes, so `<tags>`, `<authors>`, `<files>`, `<dependency>` entries and friends are hand-authored by design and survive regeneration. `module-versioning` previously said "never hand-edit `.imodspec`" in four places while `module-docs` said "edit it directly" — both wrong, in opposite directions. Corrected in 1.1.0-pre.0 by inverting the rule: state what the Software Factory owns and where each owned value is actually set, rather than what may not be touched.
- **`<summary>` and `<description>` receive the same single string**, sourced from the Application Settings page. They cannot differ, so there is no long-form field to expand into. `module-docs` used to permit "expand to max 2 sentences", which was not just wrong but unachievable — and it is what licensed an overwrought module description in a real session. The corrected guidance says one line has to serve both, and points implementation rationale at `CONTEXT.md` where it belongs.
- **Package settings are trigger rules folded into their trigger skills, not a skill of their own.** `Include in Module` (when a stereotype is introduced) and `Reference in Designer` (when a designer element is introduced) live inline in `add-designer-extension` (which absorbed `add-association-type` in 1.1.0) and `module-building-strategies`. A separate skill would have to be *remembered and loaded* exactly when the agent is busy doing the thing that creates the obligation. The general principle: **an obligation goes inline at its trigger point; a craft gets its own skill.** Element and stereotype icons sit on the craft side of that line, and since 1.1.0 they share `module-svg-icon` with the package icon rather than having a skill of their own.
- **The package icon goes through a script because of payload size, not because no other mechanism exists.** Corrected during 1.1.0-pre.0 after this was written up the wrong way round: the icon *can* be set through the MCP, but its value is a base64 data URI running to tens of thousands of characters, so routing it through an agent's context is wasteful and risks a silent transcription corruption. The rule is "use a tool that manipulates the icon element directly", not "hand-edit `.application.config` because there is nowhere else to set it". The distinction matters because the wrong version reads as a licence to hand-edit that file more generally.

- **A generated frontmatter `description` must be a single-line quoted string.** A value spanning
  multiple physical lines is silently truncated to its first line by this project's frontmatter
  parser — and if the folded `>` form is used with no text on the same line, the value is dropped
  entirely. `known-build-gotchas` had been shipping with a three-line description reduced to its
  first line since it was written, with nothing reporting it; a two-line rewrite in 1.0.2-pre.0
  produced an empty value. Caught only by reading the staged diff, where the `-`/`+` sides showed
  the truncation directly. The same defect was fixed for `module-docs`/`module-svg-icon` in 1.0.1 —
  it is a property of the parser, so it applies to every generated frontmatter block, not those
  skills specifically.
- **Never begin a generated markdown line with `**bold**`.** (2026-10 note: no longer reproduced. The rendered `file-builder-expert` troubleshooting resource has 43 lines starting with `**Symptom:**` / `**Fix:**`, all intact, and 34 were already intact before the Intent.Common 3.11.9 parser fix. The trigger may have been narrower, or fixed earlier. Keep avoiding it in new text until someone identifies the exact trigger.) The emitted line comes out as
  `- *bold**` — the leading `**` is rewritten into a list marker plus a stray asterisk, and the
  emphasis is lost. This is why several shipped instruction files (`exception-guidelines`,
  `module-building-workflow`) carry stray `- **` line openings mid-paragraph. Put the bold inside
  the sentence (`Your job is to **tell the user, not configure it**.`) rather than leading with it.
  Bold is safe anywhere that is not the first characters of a line, including after a list marker
  (`1. **Regenerate**`) — those are unaffected.
- **Promoting a module to final by hand-editing `.imodspec` strands the designer, permanently.**
  `<version>` is written only when the designer's value sorts strictly higher than the one on disk,
  so a hand-promotion that sets the manifest without moving the model leaves the designer on a
  value that can never be written again — silently, with no error on any subsequent run. Found in
  1.0.2-pre.0: the manifest read `1.0.1` while the designer still read `1.0.1-pre.4`. Clearing it
  requires the sanctioned inverse — drop `<version>` by hand to a value below the target, set the
  designer to the version you actually want, then regenerate forward. Expect the next Software
  Factory run to flag that as a destructive change; it is overwriting the hand-edit on purpose.

- **A prerelease cycle restarted after a final release must move past that release's number, never reuse it.** Found in this line of work: `1.0.2` shipped as a final release, and the next two commits set the designer to `1.0.2-pre.0` then `1.0.2-pre.1` — both sorting *below* the already-published `1.0.2` by semver precedence, so any rebuild at either value was silently shadowed by the published copy. `module-version-increment`'s own gate would have caught this (`1.0.2` already published is "at or beyond" `1.0.2-pre.1`), but the gate was never re-run after the final release shipped. Corrected to `1.0.3-pre.0`. The general lesson: the gate must run again once a version is confirmed published, not just once per task — see `Intent.ModuleBuilder.AI.Workflow`'s own gate/hook work, which exists partly to catch exactly this class of miss mechanically.
- **`module-docs`'s release-notes wording corrected to match the Software Factory's own behavior.** It previously said only maintain an entry "if the file already exists, or the maintainer explicitly asks for one to be created" — but the Software Factory is what creates `release-notes.md`, once `Module Settings → Include Release Notes` is ticked and the Software Factory runs. An agent asked to create the file should point at that setting and regenerate, never write the file by hand. Corrected alongside `Intent.ModuleBuilder.AI.Workflow`'s `module-docs-chore`, which had the identical gap.
- **`module-versioning` now distinguishes `saveOnSuccess` from a Software Factory run explicitly.** `run_designer_script`'s `saveOnSuccess` persists the designer model only; `.imodspec`'s `<version>` is generated output that only a Software Factory run produces. The skill previously implied one linear "set it, then regenerate" step; it now states that `saveOnSuccess` never substitutes for the regeneration step, since the model and the manifest are different files reached by different write paths.
- **`file-builder-expert` gained a rule against unconditional `AddUsing`.** Two shipped bugs traced to the same cause: a using added because code once spelled out a type from that namespace survived after the code was rewritten to reach it another way (`var`-typed reflection calls; a type name moved into a raw statement string). The fix in both cases was resolving the type through `UseType("Namespace.Type")` so the using tracks the reference, reserving `AddUsing` for namespaces needed independent of any spelled-out type.

- **Every C# sample must compile against Module Builder's default floors (`Intent.Common` 3.7.2, `Intent.Common.CSharp` 3.8.0), or the skill names the version to raise to beside it** (1.0.4). These skills ship to third-party module authors, who start at those floors. An API above them is kept, with its version stated, rather than dropped: `RepresentedModel` 3.8.5, `AddNestedRecord` 3.9.6, interactions 3.9.1, two-argument mapping resolvers 3.9.2, `EmitOrPublish` (Intent.Common) 3.9.0, collection/switch-case `Parent` 3.10.12. `FriendlyException` needs `Intent.SoftwareFactory.SDK` 3.9.0, above the 3.7.0 Module Builder adds - the old "no extra package reference is needed" was wrong for a fresh module. Samples were checked by compiling them in scratch projects pinned to the floors; when a sample changes, compile it again the same way.
- **No Intent-internal code in shipped skills.** `Intent.Modules.Constants` / `TemplateRoles` is not on nuget.org, so roles are literal strings, with one table in `intent-module-orchestrator` (the constant names appear only as a translation column, and the `Domain.Entity.Primary` trap is called out: the constant of that name is `"Domain.Entity"`). Samples use placeholder ids and stereotypes (`My.Module.*`, one "My Settings" stereotype) rather than other modules' templates; Intent.Modules.NET helpers such as `FilterMessagesForThisMessageBroker` and the internal `CallEntityServiceInteractionStrategy` are not taught as SDK. Values were copied from Intent.Modules.NET's `TemplateRoles.cs`, never guessed.
- **New rules are appended after existing "Must"/"Must Not" items; existing numbers never change.** Other skills and rules cite them by number (e.g. `known-build-gotchas` points to `file-builder-expert` Musts #7).
- **Mapping resolvers are taught to call `next?.Invoke(...)`, not `next(...)`.** Intent's own `EntityPatchMappingTypeResolver` returns null for mapping types it does not handle, so a later two-argument resolver can be handed a null `next`.
- **AI task providers are deprecated (user decision, 2026-10-14).** Modules carry AI guidance through designer `AI Settings` → `Rules` and generated `SKILL.md` files; the loss of proactive "this handler still needs writing" flagging is an accepted gap. `module-building-strategies` §5 carries the rule and lists them under "Patterns you'll find but must not copy".
- **`module-svg-icon` is the only skill allowed to edit `.application.config`, by user decision.** Rejected: `update_application_settings(icon=...)`, which would route the base64 payload through the agent's context. Every other skill reads settings through `run_solution_query` → `getApplicationSettings({ search })` and writes them through `update_application_settings`. `.application.config` holds no per-element icons (only the root icon, one per metadata location and one per module-settings group); element icons are emitted into `.designer.settings`. The earlier claim otherwise was wrong in both icon skills.
- **The doc skills never label anything beta, preview or pre-release (user decision, 2026-10-14)** - in release notes, READMEs, summaries, descriptions or tags.
- **"Implement here" bodies default to `Body = Mode.Ignore`; the old "Ignore is off the table" rule is reversed (user decision, 2026-10-15).** With AI writing handler bodies, a Merge body is a poor fit: Intent tracks its own lines against its previous output and keeps changing and removing them, and the agent cannot see which lines those are. Rule now: one owner per body. Generated code goes in fully managed members, code a developer or AI writes goes in an `IgnoreBody()` member with a `NotImplementedException` stub, and a mixed body is split by moving the generated part into its own member the ignored body calls. Merge stays where `CONTEXT.md` or the developer says a body is shared (Intent.Modules.NET's handler templates, which went to Merge plus `// IntentInitialGen` in 2025-08), or, as the agent's own choice, only for a body that collects generated lines from several templates or modules (a DI registration method) - a 2026-10-16 review found "genuinely interleave" let an agent talk itself into Merge for a handler. Rejected: switching existing templates' modes, which freezes or starts rewriting consumers' code; that stays a per-module developer decision. Consequence: the regeneration-baseline gate cannot check an ignored body on the reference app, so the from-scratch run checks its stub.
- **`// IntentInitialGen` never reaches the generated file** (the 2025-08 "What's new" docs: "only visible in the template source code"). Generated skills must find pending work by the `throw new NotImplementedException(...)` stub, not the marker.
- **Large work templates only proven patterns (user decision, 2026-10-15).** Prompted by agents given a full specification building every template at once on code nobody had run. Small work (a change to one template, or a single new template) is exempt, and an agent unsure of the size asks; large work with an unproven pattern stops and asks the developer. With a developer-supplied plan, the plan sets the checkpoints; without one, the agent asks whether to continue on its own or stop for review.
- **`module-svg-icon` designs icons as well as crafting them, renders before it applies, and applies only on approval of the image (1.0.4-pre.1).** Taken from a handover of a session that designed the Mediator modules' icon. Its premise had been "take the description exactly as supplied, never invent one", but a developer can reasonably ask for the design itself; a supplied description, such as the one `module-docs-chore` sources, is still used as given. What changed, and why:
  - **Design steps** (look at the current icon and the neighbouring modules' icons, draft three or four concepts as real SVGs, ask whether each says what the module *is*) because the first Mediator concept, code brackets around a diamond, said "fast generated code" rather than "mediator", and the right one, a hub joined to four parts, is the pattern's own diagram.
  - **Measured legibility rules** at 16px, where 1px is 3.125 units (gaps of about 1px, no detail under about 4px, glyph 55–60% of the badge, about 6 units of edge margin, white at 3:1 or better against the stops it sits over). Each one was broken by a draft that looked fine as source: a 0.5px gap blurred two shapes together, a 2.8px bolt became a dot. The skill's teal example uses computed WCAG ratios (white on `#2dd4bf` 1.86:1, on `#0d9488` 3.74:1). The handover's corrected gradient still starts at `#14b8a6`, which is 2.49:1, so the rule is about the stops the glyph actually sits over, not the whole gradient.
  - **Render and review in headless Chromium** at 16–128px on light and dark, with a nearest-neighbour pixel zoom and a module-list mock-up, because most problems showed only there, and Intent Architect renders with Chromium. Tested on Windows with Edge on 2026-10-20: the command as written works, and the media query hides a detail at 16 and 24px and shows it at 32 and 64px. The pixel zoom is a canvas drawn at 16px and shown with `image-rendering: pixelated` in the same sheet, tested the same way, which replaced ImageMagick and `System.Drawing` (one not installed by default, the other Windows-only). Dropped from the handover: "a non-ASCII output path fails silently", which did not reproduce from PowerShell or Git Bash.
  - **Checked by the agent evals `I1` and `I2`** (`Tests/AgentEvals`, Claude Code with Sonnet, 2026-10-20). The first run found two leaks of the base64 payload into the agent's context. Reading the `.imodspec` whole printed its `<iconUrl>`, so the skill now says to filter that line out. A PowerShell hash helper named `H` ran `Get-History`, whose error echoed the whole data URI. I had dropped that trap from the handover as a one-off quirk an hour earlier; the eval showed an agent reproducing it unprompted, so it is back in Step 6, with the reason it matters here.
  - **I2 on Claude Code's default model (Haiku) found three more weak spots (1.1.0, 2026-10-20).** (1) Step 5 told the agent to confirm with `get_file_diffs` that only `<iconUrl>` changed, and that diff prints the new value, so the skill leaked the payload by instruction; it now confirms by `git diff --stat` counts and leaves the value to Step 6's hashes. (2) The agent peeked at `.application.config` with `cut -c1-100` to "see its structure", despite "never open, read or print the file": the root `<icon>` line starts with the payload, so even a truncated line leaks it. The skill now names the leaking commands, offers counts (`grep -c`) as the only safe look, and carries a ready-made, tested apply script, because an agent with nothing to write has nothing to look up. (3) With "`module-version-increment` decides, if available", the agent judged the version published from the release notes and stopped to ask about a bump the user never raised; the skill now says to load that skill's gate, never judge from release notes, and without it apply and name the version for the developer to check. After the fix: I2 3/3 on Haiku, and I1, I2 and R3 still pass on Haiku and Sonnet.
  - **Size-dependent detail through an SVG media query**, which falls back to full detail where unsupported.
  - **An approval gate on the rendered image.** That session applied an icon chosen from a list of described concepts and had to redo it after it was applied. The gate also holds when another workflow calls the skill: with no one to approve, the icon stays unapplied and the renders are reported. This changes `module-docs-chore`'s icon step in practice, which is accepted: an icon is the module's face, and applying one unseen is the failure the gate exists for.
  - **Apply only the `.imodspec` from the Software Factory run, then verify by hash** across the approved SVG, `.application.config`, `.imodspec` and the built `.imod`, because each run there also staged unrelated files, and a hash proves the icon reached each file without anyone reading the payload.
  - **The edit-tools rule.** `AI.Workflow`'s instructions say to change files with edit tools, never a shell script, and its gate denies edit-tool writes to `.application.config` anyway. The skill names itself the exception to that rule too, scoped exactly like the off-limits exception, rather than rerouting through `update_application_settings`, which reintroduces the payload problem.
- **15 skills trimmed to 10 in 1.1.0 (user decision, 2026-10-20).** The goal is fewer skill triggers first and fewer tokens second, without losing effectiveness. Every skill's description is listed in every agent session, and overlapping descriptions make routing harder. Merged: `add-association-type` into `add-designer-extension` (it already used that skill's reference through a `../` path and repeated its package-settings table and designer ids); `module-element-icons` into `module-svg-icon` (it told agents to follow the svg skill's house style verbatim, and about 40 lines across the two only explained where one ended and the other began); `intent-mapping-architect` into `file-builder-expert` as a resource plus a short Musts section (mappings are only generated inside a C# template, where that skill is already loaded); `module-debugging` into `file-builder-expert`'s troubleshooting resource § 15, with a one-line pointer from `known-build-gotchas` so Markdown-template authors still find it. Its designer-script half was dropped, because Intent's own `scripting-the-model` skill already covers `console.log`. Kept separate: `intent-metadata-consumer` (it also serves factory extensions and Markdown templates, which `file-builder-expert`'s description excludes, and AI.Modelers names it), `intent-module-orchestrator` (a separate decision, cross-module wiring, with an 878-line cheatsheet that would swamp `file-builder-expert`'s Musts), and `module-versioning` / `module-docs` (AI.Workflow's `module-docs-chore` relies on `module-docs` being opt-in only). **Rule for any future merge: the surviving skill keeps a name other modules already reference** (`module-docs`, `module-svg-icon`, `file-builder-expert`, `intent-metadata-consumer`, `module-building-strategies`), so no other module has to change.
- **Interaction strategies are deprecated (user decision, 2026-10-20).** An AI agent writes business logic better than a deterministic `IInteractionStrategy` can, so the guidance must not propagate it: `intent-domain-interactions-expert` was deleted outright, not folded, and `module-building-strategies` lists interaction strategies under "Patterns you'll find but must not copy". The mapping content was kept, with its interaction framing removed: mappings still drive structural generation. The warning against taking an `Intent.Application.DomainInteractions` dependency for `GetUpdateEntityMapping()` stays, because it protects against exactly that dependency.
- **Routing evals R1–R5 measure this module's skills (2026-10-20).** `Tests/AgentEvals/RoutingScenarios.cs` asks a how-to question each skill should answer and checks both the skill load and a marker the answer must contain. A route accepts any of several skills, so the same scenario scores before and after a merge. Wording matters: a prompt that said "answer from whatever guidance you have" let the agent answer from the skill descriptions alone, without loading anything. On Claude (Haiku), the baseline before the trim was 15/15 and after it 14/15; the one miss grepped the merged skill file instead of loading it, and its answer was still right. Run them before and after any change to which skills exist.
  A marker has to be something only the right answer says: R3's first marker (`UrlImagePath`, a data URI) is in
  the package-icon procedure too, so it could not catch the confusion the icon merge risks. A keyword check for
  that route then failed correct answers that mention the package icon only to rule it out, so R3 carries a
  judge brief that scores which route the answer took instead. After the review fixes: 15/15, three runs.
- **A rule folded into a resource is out of reach for a weaker model (2026-10-21).** The 15-vs-10 comparison
  (cases C1–C25 in `Tests/AgentEvals/SkillCoverageScenarios.cs`, written by an independent agent from the old
  skills only) found one regression: `module-debugging` said in its body that `Logging.Log` has no `Error`
  level; after the merge that sentence lived only in `file-builder-expert`'s troubleshooting § 15. Haiku loaded
  the skill, never opened the resource, and copied the skill's `Logging.Log.Debug` example (0/6, from 6/6);
  Sonnet opened it (6/6). Fixed by stating the levels in the skill itself. **Rule for any future merge: a fact an
  agent needs to get the common case right stays in `SKILL.md`; a resource holds detail, never the only copy of
  a must.** Agents also often grep the skills folder instead of loading a skill, so the evals count a skill as
  found when its text reached the agent by any route.

## Invariants & Constraints

- Every skill's `File Template` (type `Single File`) sits directly under the `Skills/` folder, named `<SkillName>_SkillMd_Agents` (and `<SkillName>_Resources...` for resource files) — there is no per-skill subfolder. `File Settings(Output File Content=Text, Templating Method=Markdown File
  Builder)`; `Template Settings(Source=Lookup Type, Role=AI.Context.Skills)` with `Default Location` left **unset**. New skills should mirror this flat shape exactly — see `ModuleVersioning` or `ModuleSvgIcon` as reference.
- The `MarkdownFile` constructor's `relativeLocation` argument carries the real output path directly — e.g. `new MarkdownFile("SKILL", relativeLocation: "module-versioning")` — never the `Template
  Settings.Default Location` model setting. `Default Location` only ever seeds that argument's value at the moment a File Template is first created; the constructor's `Body = Mode.Ignore` means the model setting is never read again afterward, so leaving it set is misleading. See the `local-add-module-skill-template` skill's mechanism step 6 for the full anchor-resolution rules.
- This module has no `Module Settings Configuration`/settings of its own — every bundled skill is unconditional. Gating by setting belongs to `Intent.ModuleBuilder.AI.Workflow`, not here.

- `release-notes.md` headings track the **eventual released version, never the in-flight pre-release
  version**. Work done across `1.0.2-pre.0`, `-pre.1`, … accumulates under a single
  `### Version 1.0.2` heading. Confirmed by the file's own history: the `### Version 1.0.1` section
  absorbed work `CONTEXT.md` attributes to `1.0.1-pre.1`, `1.0.1-pre.3` and even `1.1.0-pre.0`, and
  no `-pre.N` heading has ever appeared. The module's `<version>` genuinely is the pre-release string
  while in flight — the heading is the exception, not a mirror of it.
- **A version raise in skill text names the whole chain, down to `Intent.SoftwareFactory.SDK`.** Module
  Builder scaffolds direct references to `Intent.Modules.Common` 3.7.2, `Intent.Modules.Common.CSharp` 3.8.1
  (the `.imodspec` floor is 3.8.0) and `Intent.SoftwareFactory.SDK` 3.7.0, plus `Intent.Persistence.SDK`
  1.0.1-alpha.2 once a Version Migration exists. Raising one package pulls the next: Common.CSharp 3.8.5–3.9.2
  needs Common 3.7.3, 3.9.6 needs 3.9.1, and 3.10.12 needs 3.11.0. Common 3.9.0–3.9.1 needs SDK 3.10.0, 3.9.2

## Module Interactions

- **Intent.ModuleBuilder.AI.Workflow** — a separate module bundling conditional, process-shaped workflow skills (version increment timing, doc-chore cadence, context capture). No package dependency is declared between the two modules, and that stays deliberate — each bundle must remain independently installable. The one exception: AI.Workflow's `module-docs-chore` names `module-svg-icon` by name, but only as a **soft, conditional** pointer ("if the skill is available in your environment, use it") gated behind its own `MaintainModuleIcon` setting — never assumed present. Do not upgrade this to a declared dependency without a deliberate decision to do so; keep any further cross-references to this same soft-pointer shape.
